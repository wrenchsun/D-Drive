このツール（`Tools/SpecWeb/`、Google Apps Script）は現在ユーザー個人
（`yamaguti1013katuya@gmail.com`）が運用者兼 GAS プロジェクトの所有者になっている。
本書は「別の誰かが運用者を引き継いでも成り立つ」ための手順書であり、実データ
（実際のデプロイ URL・トークンの値・実名・実際のスプレッドシート ID）は一切書かない。

> Google アカウントに紐付く実行環境**である。引き継ぐべきものは「コード」ではなく
> 「このアカウント固有の実行環境と、そこに保存された実データ」である。

## 1. 引き継ぎの全体像（何が「アカウント固有」か）

| # | 対象 | 現在の所有者 | 引き継ぎが必要な理由 |
|---|---|---|---|
| 1 | Apps Script プロジェクト本体 | 運用者個人の Google アカウント | コードのオーナー権限・実行権限がアカウントに紐付く |
| 2 | デプロイ①（人向け SPA） | 同上（実行ユーザー = アクセスした人） | URL は変わらないが、デプロイの「管理」操作は編集権限を持つ人しかできない |
| 3 | デプロイ②（D-Drive API） | 同上（実行ユーザー = 自分＝所有者） | **実行ユーザーが「自分」固定のため、所有者が変わると Unity 側からの同期が止まる**（後述） |
| 4 | Drive 上の JSON ストレージフォルダ（`assets.json` 等） | 運用者個人の Google アカウント | `Storage.js`（`DriveAdapter`）が読み書きする実データの置き場所 |
| 5 | Drive 上の画像フォルダ（添付画像・アイコン等） | 同上 | `referenceImages` 等が指す `driveFileId` の実体 |
| 6 | ガント スプレッドシート（企画担当が所有） | **企画担当個人の Google アカウント**（SpecWeb の運用者とは別人） | SpecWeb の運用者は「ガントの URL」を設定するだけで、シート自体の所有権は動かさない（後述） |
| 7 | スクリプトプロパティ（トークン・ガント URL） | Apps Script プロジェクトに紐付く | プロジェクトの所有者が変わっても値は残るが、**新しい運用者が値を把握できていないと再発行が必要になる** |
| 8 | `users.json`（ログイン許可リスト） | Drive 上のデータ（プロジェクトではなくデータの一部） | 「誰が admin か」を持つため、admin が 0 人になるとロックアウトする |
| 9 | Unity 側 `DDriveSpecSettings`（`.asset`。`WebAppUrl`/`HumanAppUrl`）+ `EditorPrefs`（トークン） | 各開発者のマシン | URL 自体は変わらない前提だが、トークンをローテーションしたときは全員のマシンで再設定が要る |

**デプロイ②が「実行ユーザー = 自分」である**（README §7）ことが最重要ポイントである。
これは「誰がアクセスしても、コードは所有者の権限で実行される」という意味であり、
**GAS プロジェクトの所有者が変わっても、デプロイ②の URL 自体は変わらない**
（Apps Script のデプロイは「バージョンへの固定リンク」であり、所有者移管では自動的には
再作成されない）。ただし、**デプロイの「編集」操作（新バージョンへの更新等）は
エディタへの編集権限を持つ人にしかできない**ため、旧運用者がプロジェクトへのアクセスを
失う（アカウント削除・退職等）前に、新運用者へ編集者権限を渡しておく必要がある。

## 2. (a) 所有者の移管

### 2.1 Apps Script プロジェクト

Apps Script プロジェクトの「オーナー」自体を移管する公式な機能は無い
（Google ドキュメント/スプレッドシートのような「オーナーを譲渡」は Apps Script
プロジェクト単体には無い）。実務上は次のどちらかで対応する。

- **(推奨) 新運用者を編集者に追加し、新運用者が新しいデプロイ②を作る**: Apps Script
  エディタ右上の共有設定（またはプロジェクトのバインド先スプレッドシート/Drive の共有設定）
  から新運用者を編集者に追加する。**旧運用者のアカウントが使えなくならない**前提なら、
  実運用としては「デプロイ②の実行者を新運用者に切り替える」ために、新運用者が
  一度ログインした状態で新しいデプロイ②を作り直し、Unity 側の `WebAppUrl` を新しい URL に
  差し替える方法が最も確実（旧デプロイ②は動作確認後に「アーカイブ」する）
- **プロジェクトの Drive 上のファイルとしての所有権を移す**: スタンドアロンの Apps Script
  プロジェクトは Drive 上では 1 個のファイルとして扱われるため、Drive の「所有者を変更」機能
  （旧所有者が Google Workspace に所属している場合は使える、個人 Gmail 同士でも「所有権の移動」
  リクエストを送って相手が承認すれば移せる）で所有者自体を移せる場合がある。ただし
  **デプロイ①②はそれぞれ「実行ユーザー」の設定を持っており、所有権移動後にその設定が
  意図通りかを毎回確認すること**（README §7 の「② D-Drive API には `clasp update-deployment`
  を使わない」と同じ理由で、意図しない実行ユーザーに変わっていないかは UI で目視確認する）

いずれの方法でも、**移管後に実施すること**:

1. 新運用者が Apps Script エディタを開けることを確認する
2. デプロイ①②それぞれの「デプロイを管理」画面で、実行ユーザー・アクセス権が
   README §7 の表（① アクセスしているユーザー / Google アカウントを持つ全員、
   ② 自分 / 全員）のままであることを確認する
3. 新運用者が `clasp login` を自分のアカウントで行い、ローカルの `.clasp.json` の
   `scriptId` を（新しく作った場合は新しい ID に）差し替える

### 2.2 Drive の JSON ストレージフォルダ

`SPEC_WEB_DRIVE_FOLDER_ID`（スクリプトプロパティ、README §4）が指す Drive フォルダ。

1. Drive でフォルダの共有設定を開き、新運用者を「編集者」として追加する
2. 所有権自体を移す場合は、フォルダを右クリック →「所有権を譲渡」（同一 Google
   Workspace 内、または個人アカウント間でも譲渡リクエスト→相手の承認で可能）
3. **フォルダ ID 自体は変わらない**ため、所有権を移しただけならスクリプトプロパティ
   `SPEC_WEB_DRIVE_FOLDER_ID` の変更は不要。フォルダを新規に作り直した場合だけ、
   このプロパティを新しい ID に更新する

### 2.3 Drive の画像フォルダ

添付画像・アイコン等（`referenceImages` が指す `driveFileId` の実体）を置いているフォルダ
（`DriveAdapter` の画像用フォルダ。存在する場合）も、上記 2.2 と同じ手順で共有・移管する。
**フォルダを作り直すと `driveFileId` が一致しなくなり、既存の添付画像が表示できなくなる**
ため、フォルダは作り直さず共有・所有権移動だけで済ませること。

### 2.4 ガント スプレッドシートの所有権・アクセス権

ガントのスプレッドシート「03_ガントチャート」は**企画担当が所有するファイルであり、
SpecWeb の運用者が所有・管理するものではない**（docs/32 §10.5 の前提）。SpecWeb 側が
持つのはこのシートへの **URL（設定値、`settings.setGanttUrl`）だけ**であり、シート自体の
所有権・アクセス権は企画担当側で管理する。運用引き継ぎ時に SpecWeb 側でやることは:

1. 新しい運用者（admin）が「メンバー」画面の「ガントの URL の設定」を開き、現在の
   URL が引き続き正しいか確認する（企画担当が変わった、シートを作り直した等の場合は
   企画担当から新しい URL を受け取って再設定する）
2. `createGanttTemplate()`（本書 §3 と README「ガント テンプレート」参照）で新しく
   テンプレートを生成した場合は、**生成したスプレッドシートの所有者は実行した運用者の
   アカウントになる**。企画担当が別アカウントで運用する前提なら、生成後に企画担当へ
   ファイルの所有権を譲渡すること

## 3. (b) スクリプトプロパティの引き継ぎと再発行

スクリプトプロパティは Apps Script プロジェクトに紐付く（Drive のファイルではない）ため、
プロジェクトの編集権限を持つ人なら誰でも「プロジェクトの設定」→「スクリプト プロパティ」
から値を見られる。ただし**トークン系の値は README §6 の方針により発行時にログへは残さない**
ため、**引き継ぎのタイミングで値を直接確認する術がない場合がある**。

| キー | 用途 | 保存先 | 引き継ぎ時の対応 |
|---|---|---|---|
| `SPEC_WEB_DRIVE_FOLDER_ID` | データフォルダの Drive ID | スクリプトプロパティ | プロジェクトの設定画面でそのまま確認できる（秘匿情報ではない） |
| `SPEC_WEB_TOKENS_READ` | 読み取り用 API トークン（配列、JSON文字列） | スクリプトプロパティ | 値を直接見れば分かるが、**新運用者への引き継ぎでは値を見せず、`rotateApiToken('read')` で新しいトークンを発行し直すことを推奨**（旧運用者が値を保持したまま離任すると、後から失効させにくい） |
| `SPEC_WEB_TOKENS_WRITE` | 書き込み用 API トークン（配列、JSON文字列） | スクリプトプロパティ | 同上。**Unity 側で使っている値のため、ローテーション後は全開発者の `DDriveSpecSettings` 設定画面（Unity Editor）で再設定が必要**（§6 参照） |
| `SPEC_WEB_SETTINGS_GANTT_URL` | ガントの URL | スクリプトプロパティ | 秘匿度は中（社内共有のスプレッドシート URL）。プロジェクトの設定画面で確認できる |

### 引き継ぎ時に推奨する手順（トークンは「見せずに作り直す」）

1. 新運用者を admin として `users.json` に追加する（§4）
2. 新運用者が Apps Script エディタから次を実行し、新しい READ/WRITE トークンを発行する
   （README §6 のローテーション手順と同じ）:
   ```js
   function handoverRotateTokens() {
     Logger.log('新しい READ token: ' + rotateApiToken('read'));
     Logger.log('新しい WRITE token: ' + rotateApiToken('write'));
   }
   ```
3. 新しいトークンを、既存の連絡手段（後で消せるチャンネル等。git や Slack の履歴に残る形は NG）
   で必要な開発者に配布し、各自の Unity Editor（`DDriveSpecSettings` の設定画面）で再設定する（§6）
4. 全員の再設定が終わったら、旧トークンを失効させる:
   ```js
   function handoverRevokeOldTokens() {
     revokeApiToken('read', '旧READトークンの文字列');
     revokeApiToken('write', '旧WRITEトークンの文字列');
   }
   ```
   旧トークンの文字列が分からない・漏洩の懸念がある場合は
   `revokeAllApiTokens('read')` / `revokeAllApiTokens('write')` で緊急失効し、
   新トークンだけを配布し直す

## 4. (c) `users.json`（ログイン許可）の admin 引き継ぎ

- **通常の追加**（引き継ぎ前に、現運用者がまだ admin としてログインできる場合）:
  現運用者が「メンバー」画面下部「ログイン許可（users.json）」から新運用者を
  `admin` ロールで追加する（README §5 後半、O-14）。追加後、新運用者は自分の
  Google アカウントでログインし、admin としての操作ができることを確認する
- **最初の 1 人が誰もいない/admin 権限を持つ人に連絡が取れない場合のブートストラップ**:
  README §5 前半の手順（`upsertSpecWebUser(email, displayName, 'admin')` を Apps Script
  エディタから実行）を使う。この関数は **`users.json` に admin が 1 人も居ないときだけ
  無条件で実行できる**（`specWebHasNoAdmin_()`、`src/Api/UserAdmin.js`）。admin が
  1 人でも残っている状態では使えない（＝正規の admin 経由で追加してもらう必要がある）
- **admin のロックアウトに関する制約**（`src/Api/UserAdmin.js`、`users.upsert`/`users.remove`）:
  - 自分自身の admin 権限を自分で降格・削除することはできない
  - admin が 1 人しかいない状態では、その 1 人を他の誰かが降格・削除することもできない
  - そのため、**旧運用者が離任する前に、必ず新運用者を admin として追加し、
    新運用者が admin としてログインできることを確認してから**、旧運用者自身のロールを
    下げる・削除するという順序を守ること（先に旧運用者を消すと、新運用者が誰も admin に
    なれない状態を作りかねない。ただし上記のブートストラップ経路があるため復旧は可能）

## 5. (d) デプロイの更新手順（引き継ぎ後の初回更新で必ず確認すること）

引き継ぎ後、初めてコードを更新して反映するときは README §7 の手順をそのまま使うが、
次の 2 点は引き継ぎ特有の確認事項として強調する。

1. **② D-Drive API は必ずエディタの UI から「新バージョン」に更新する**
   （`clasp update-deployment`/`redeploy` を使わない）。README §7 に記載のとおり、
   このコマンドはマニフェストの `webapp` 設定（① 相当の設定）でデプロイの実行ユーザー・
   アクセス権を上書きしてしまい、**② が「自分 / 全員」から変わって Unity からの
   `?api=1` が Google ログイン画面に弾かれる**（2026-09-19 に実際に発生した事故と同じ）。
   引き継ぎ直後は特に、新運用者がこの制約を知らずに `clasp` コマンドで済ませようとして
   事故る可能性が高いため、**このセクションを必ず新運用者に共有すること**
2. **push 前にブラウザの Apps Script エディタタブを閉じる/再読み込みする**
   （README §13 末尾と同じ注意。引き継ぎ直後は新運用者がエディタを開いたまま
   `push.cmd` を実行しがちなので、事前に共有しておく）

## 6. (e) Unity 側（D-Drive）の再設定

`DDriveSpecSettings`（`Assets/GameData/Settings/DDriveSpecSettings.asset`。
`Assets/DDrive/Editor/Spec/DDriveSpecSettings.cs`）が持つ設定は次の 2 種類:

| 項目 | 保存先 | 引き継ぎで変更が要るケース |
|---|---|---|
| `WebAppUrl`（デプロイ②の URL）/ `HumanAppUrl`（デプロイ①の URL） | `.asset`（**git 管理・チーム共有**） | 所有者移管で URL 自体が変わらない限り変更不要。**新しくデプロイを作り直した場合のみ**、この 2 つを新しい URL に更新し、コミットしてチームに周知する |
| API トークン（READ/WRITE） | `EditorPrefs`（**マシンごと**。`DDrive.SpecWeb.ReadToken:<プロジェクトの絶対パス>` 等のキー） | **トークンをローテーションしたら、開発者全員が各自の Unity Editor で再設定する必要がある**（.asset には書かれないため、git 経由では配れない） |

再設定の手順（各開発者が自分のマシンで行う）:

1. Unity Editor で D-Drive の「仕様書と同期」設定画面（`SpecSyncWindow`、既存の
   `DDriveSpecSettings` 相当の UI）を開く
2. URL が変わっている場合は `WebAppUrl`/`HumanAppUrl` を新しい値に更新する
   （`.asset` の変更なので、1 人が更新してコミットすれば他の人は `git pull` で反映される。
   ただし Unity Editor の UI から設定した場合は `Undo.RecordObject` +
   `EditorUtility.SetDirty` を経由すること。CLAUDE.md §0-5）
3. トークンをローテーションした場合は、各自が新しい READ/WRITE トークンを設定画面に貼り直す
   （こちらは `EditorPrefs` なので、他の人の設定には影響しない代わりに、
   **全員が個別に再設定する必要がある**）
4. 同期を実行し、エラーが出ないことを確認する

## 8. (g) 個人 Gmail アカウント所有の制約と、Workspace へ移す場合の差分

docs/32_spec_web.md §2.3 の決定どおり、**このツールは個人の Gmail アカウントでの運用を
前提に設計されている**。理由と制約は次のとおり:

- 個人アカウントの Web アプリ デプロイには「特定のドメインに限定」オプションが存在しない
  （Workspace アカウント限定の機能）。そのため、**アクセス制御はデプロイの権限設定ではなく
  アプリのコード側の許可リスト（`users.json`）で行っている**（§2.3・§7 決定事項）
- URL Fetch 呼び出し数・トリガーの合計実行時間の上限は個人アカウントの方が Workspace より
  低いが（docs/32 §9 の制限一覧）、想定データ規模・チーム規模ではどちらの上限にも近づかない
- Drive のファイル共有・フォルダ共有は個人アカウント同士でも問題なく機能する
  （招待した相手が Google アカウントさえ持っていればよい）

**Google Workspace アカウントへ移す場合の差分**（将来、組織として運用する場合の選択肢）:

| 項目 | 個人 Gmail（現状） | Workspace に移した場合 |
|---|---|---|
| デプロイ①のアクセス制御 | コード側の許可リスト（`users.json`）のみ | 「組織内のユーザーのみ」のようなドメイン限定オプションが追加で使える（ただし本ツールは許可リスト方式のままで動作は変わらない。二重の防御として使う分には無害） |
| URL Fetch / トリガー実行時間の上限 | 低い（docs/32 §9 の表） | 高い（同上） |
| 所有権移管のしやすさ | Drive ファイルの「所有権の移動」は相手の承認が必要 | 組織の管理者がドメイン内で強制的に所有権を移せる場合がある |
| コードの変更要否 | — | **基本的に不要**。`Auth.js`/`Code.js` はドメインに依存する実装をしていないため、
  アカウント種別を変えるだけでそのまま動く想定（未検証。移行時は README §8 の
  ローカルテストと実デプロイでの目視確認を必ず行うこと） |

Workspace への移行自体は本書のスコープ外（意思決定はユーザー側で行う）。移行する場合は、
本書 §2〜§7 の手順を「個人アカウント → 個人アカウント」ではなく
「個人アカウント → Workspace アカウント」に読み替えて実施すればよい
（手順自体は変わらない）。

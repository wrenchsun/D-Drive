基本概念（Data / Instance / Handle、4層、AssetId）

D-Drive のコードを書く前に知っておくべき設計の土台をまとめます。詳細な設計根拠は docs/01_architecture.md・docs/02_core_framework.md にあります。本ページはその要約＋実際のソースで確認した実装の詳細です。

1. 4 層構成と asmdef の対応

システムは 4 層に分離されており、上の層は下の層しか知らないという一方向の依存だけが許されます（[01_architecture.md] §1）。実際の asmdef 名と参照関係は次のとおりです（Packages/com.ddrive.core/**/*.asmdef から確認）。

層asmdef主な参照役割
FoundationDDrive.FoundationUniTaskRegistry / Loader / Pool / Handle / EventBus / Pause / ValueDef / Validation の共通基盤。Unity 非依存部分は最小限
RuntimeDDrive.RuntimeDDrive.Foundation, UniTask, Unity.Addressables, Unity.ResourceManager, Unity.Netcode.Runtime, UnityEngine.UI, Unity.InputSystem種別ごとの Data / Manager / Instance / 静的ファサード（Audio・Vfx・Anim 等）、Presentation 層、起動配線（DDriveRuntimeBootstrap）
EditorDDrive.EditorDDrive.Foundation, DDrive.Runtime, Unity.Addressables.Editor, URP Runtime/Core, UnityEngine.UI, Unity.InputSystem（includePlatforms: ["Editor"]）AssetBrowser / 各専用エディタ / Preview / ID 生成（Codegen） / Validation UI
TestsDDrive.Tests.Editor / DDrive.Tests.Runtime / DDrive.Tests.Performanceそれぞれ DDrive.Foundation, DDrive.Runtime（+ Editor はさらに DDrive.Editor）EditMode / PlayMode / パフォーマンステスト。DDrive.Tests.Runtime は全プラットフォーム対象の asmdef のため PlayMode でしか実行されない
(参考) サンプルDDrive.SamplesDDrive.Foundation, DDrive.Runtime, Unity.Netcode.Runtime, UniTask, Unity.InputSystemゲームコードが D-Drive をどう呼ぶかを示すデモ（Packages/com.ddrive.core/Samples~/Demo/）。Editor 層は参照しない
Game Layer（あなたが書くゲームコード）は DDrive.Runtime だけを参照してください。 DDrive.Editor への参照はランタイムに入ると壊れるため禁止です（[CLAUDE.md] §0-3）。このリポジトリには「Game.*」用の asmdef は無く、通常はデフォルトアセンブリ（Assembly-CSharp）にゲームコードを書く前提のようです（要確認: プロジェクトとして Game 用の独自 asmdef を作る方針かどうかは docs に明記が無い）。

2. Data / Instance / Handle の分離

この分離が設計の核です（[01_architecture.md] §2）。

  • Data: ScriptableObject（AssetDataBase 派生）。定義そのもの。ロードされたら読み取り読み取り専用で、複数の Instance から共有されます。Manager は Data を書き換えません（[CLAUDE.md] §0-5）
  • Instance: Manager 内部のプールで管理される実体（位置・寿命・再生状態など可変データ）。同じ Data から複数生成できます。外部には公開されません
  • Handle: readonly struct { int index; int generation; }。ゲーム側は Instance に直接触らず、必ず Handle 経由で操作します。破棄後の Handle への操作は例外を投げず no-op になります（世代不一致で検知）。GC alloc 0。詳しくは handle.html

なぜ Data を書き換えてはいけないか: Data は複数の Instance・複数の Manager 呼び出しから同時に参照される共有の定義です。ランタイムから書き換えると、他の再生中インスタンスやマルチスレッド／ネットワーク越しの参照との整合性が取れなくなります。値を可変にしたい場合は Instance 側（Handle 経由の API）か、ValueDef／Tuning（調整値。[02_core_framework.md] §2.5・§14）を使ってください。Data をエディタから書き換える場合（専用エディタ側の実装）は必ず Undo.RecordObject + EditorUtility.SetDirty を伴う必要があります（[CLAUDE.md] §0-5）。

3. AssetId — ID の実体

実装は Packages/com.ddrive.core/Foundation/Identity/AssetId.cs。

public struct AssetId<TMarker> : IAssetId, IEquatable<AssetId<TMarker>> { public ulong Value { get; } public AssetType Type { get; } public bool IsValid { get; } // Value != 0 public static readonly AssetId<TMarker> Invalid; }
  • TMarker は空のタグ構造体（SeMarker・VfxMarker など、種別ごとに 1 つ）で、SeId と VfxId のような別種別の ID を代入できないようにする型パラメータです（using SeId = AssetId<SeMarker>; のようなエイリアスで種別ごとの名前を付けます）
  • 中身は GUID から生成した安定な ulong（enum ではありません。理由: enum は並び替え・削除でシリアライズが壊れるが、ulong は安定・高速・Burst 可。[01_architecture.md] §10 ADR#1）
  • [Serializable] ですが readonly struct ではありません。Unity のシリアライザは C# の readonly フィールドへ書き込めない（CLR 制約）ため、あえて非 readonly にして Inspector 編集・PropertyDrawer を成立させています（不変性は getter-only プロパティで担保）

生成定数（Assets/Generated/AssetIds.g.cs）

手編集禁止の自動生成ファイルです。種別ごとに <接頭辞>ID という静的クラスが生成され、その中に public static readonly AssetId<Marker> の定数が並びます。例（実ファイルより）:

public static class SEID
{
    public static readonly AssetId<DDrive.Runtime.Audio.SeMarker> PlayerSlash =
        new(0x1163AE57E590A130UL, AssetType.Se);
}

読み方: SEID.PlayerSlash は「Se 種別の、識別子 PlayerSlash」という意味です。定数名は Data の識別子から、その種別の接頭辞トークン（SE・VFX など）が先頭に付いていれば取り除いて生成されます（Editor/Codegen/AssetIdGenerator.cs の ToConstantName / KnownPrefixes）。

  • 再生成: Tools > D-Drive > Generate > Regenerate Asset IDs（メニュー定数は DDriveMenu.Generate）。アセットの作成・識別子変更のタイミングでツールが呼ぶため、通常は手動再生成を意識する必要はありません
  • asmdef の所属に注意: Assets/Generated/AssetIds.g.cs 自体には asmdef が無く、既定アセンブリ（Assembly-CSharp）に属します。そのため 独自の asmdef を持つコード（DDrive.Samples など）からはこれらの定数を直接参照できません。実際 Packages/com.ddrive.core/Samples~/Demo/PresentationSkillSlashDemo.cs のコメントにもこの制約と、生の値で AssetId<TMarker> を組み立てる回避策が書かれています。通常のゲームコード（既定アセンブリに置く場合）はこの制約を気にせず DDrive.Generated.SEID.PlayerSlash のように直接使えます
定数名の形: KnownPrefixes（SE / BGM / VFX / ANIM / ANIM2D / MAT / TEX / CANVAS / PREFAB / PRES / SHAKE / HAPTIC / HAPTICS / UITWEEN / MODEL / ANC / ANCG / SKIN / CUT の 19 個）に含まれる接頭辞はファイル名から取り除かれ、MODELID.PlayerModel / ANCHORID.AnimJump / SKINID.ButtonSkin のように種別クラス名 + 識別子だけになります。docs/42_distribution.md §5.3 により、互換性ポリシー発効（P-13）後はこの生成規則と KnownPrefixes は公開 API として固定されます。

5. 設計判断（ADR）のうち、コードの書き方に影響するもの

[01_architecture.md] §10 より、プログラマーが API を呼ぶ上で知っておくと理解が早いものを抜粋します。

判断プログラマーへの影響
ID は enum でなく生成定数 + ulongSEID.PlayerSlash のような定数を直接比較・キーにしてよい。enum のような並び替えは起きない
Handle は class でなく struct + 世代Handle をフィールドに持ち回しても GC を増やさない。破棄後にアクセスしても例外にならず no-op（handle.html 参照）
Manager は DI 可能なサービス + static ファサードゲームコードからは Audio.PlaySe(...) のような static ファサードを呼ぶだけでよい。テストでは実体（AudioManager 等）を差し替えられる
プレビューは実行時 Manager を Editor で駆動Editor 専用の再生経路が無いので、ランタイム API はエディタのプレビューとゲーム実行時で常に同じ挙動になる
イベントは UnityEvent でなく独自 AssetEventFrame/Time/Custom トリガでの SE・VFX 発火はデータ側で完結し、コード側でイベント配線を書く必要はない（[02_core_framework.md] §3）
調整値は ValueDef に統一種別をまたいで同じ評価 API（Evaluate(t)）になる。HP 等の単純な調整値は別枠の Tuning（TUNING.キー定数 / Tuning.GetFloat(...)）を使う（[02_core_framework.md] §14 5-13 追記）

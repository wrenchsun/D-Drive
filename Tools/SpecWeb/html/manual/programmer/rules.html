コーディング規約・禁止事項

このページは「守らないと CI が赤くなる」規約を実用の観点でまとめたものです。設計原則の背景は 基本概念、PR を出す前の全チェック項目は docs/12_review.md を参照してください。

禁止 API

Assets/DDrive/Editor/Validation/ForbiddenApiScanner.cs が、Assets/DDrive 配下の全 .cs ファイルをテキストパターン一致（正規表現）で走査します。Roslyn Analyzer ではなく簡易的なテキスト走査です。

#禁止パターン（正規表現）代わりに使うもの許可されているファイル
1\bTime\.(time|deltaTime|unscaledDeltaTime|timeAsDouble|unscaledTime)\bITimeSource（docs/02_core_framework.md §9.5）LocalTimeSource.cs / NetworkTimeSource.cs / GameLoopDriver.cs
2\bResources\.Load\bAddressables 経由（IAssetLoader）（例外なし）
3\bAddressables\.Load\w*\bIAssetLoader 経由AddressablesAssetLoader.cs
4\b(?:UnityEngine\.)?Object\.Instantiate\s*\(|(?<![.\w])Instantiate\s*\(PoolService 経由PoolService.cs / PreviewService.cs（非破壊ループ試聴用の ScriptableObject コピーを許可）
5\bAudioSource\.Play\bAudioManager 経由（例外なし）

いずれのルールも ForbiddenApiScanner.cs 自身は常に例外扱いです（このファイルの Message 文字列がパターンに一致してしまうため、自己検出を避ける自己参照の除外）。// で始まる行（コメント）はどのルールも対象外です。

スキャナは Samples/ フォルダを走査対象外にしています。 Assets/DDrive/Samples/ 配下（NetBridgeSmokeTest.cs 等の手動確認用デモ）はパスに /Samples/ を含む場合、ルールに関係なく丸ごとスキップされます。
ゲームコード（Assembly-CSharp 等）はこのスキャナの対象外です。 Editor/Validation/CI.cs は ForbiddenApiScanner.Scan("Assets/DDrive") という固定パスでしか呼んでおらず、D-Drive 本体以外のフォルダは走査しません。それでも CLAUDE.md §0-3 は同じ禁止事項（Instantiate / Resources.Load / AudioSource.Play の直接呼び出し）をゲームコードにも適用すると定めています。ゲームコードでこれらの API を直接呼んでも CI は検出しません。人が守るしかないことを理解したうえでレビューしてください。

定常経路（Tick / Spawn / Play）でのパフォーマンス規約

毎フレーム、または高頻度に呼ばれる経路（Tick / Spawn / Play）では LINQ・クロージャ・boxing を禁止します（docs/12_review.md §3）。

2026-09-15（6-2）から自動検証があります。 Assets/DDrive/Tests/Performance/（asmdef DDrive.Tests.Performance、com.unity.test-framework.performance 使用）が、Pool の Rent/Return・Vfx/Se/CameraFx/Haptics の Tick・Presentation の Tick+Signal・GameLoopDriver の 1 フレームなど、Tick 系の定常経路を GC.GetAllocatedBytesForCurrentThread() の差分で hard assert します。-testCategory Performance で実行します（Unity Test Runner、または Tools/CI/run-ci.cmd の [5/6]）。GitHub Actions での自動実行は P7 末の CI 導入まで保留されているため、現状はローカル実行が唯一の実行経路です。

既知の未解決 alloc（このチェックでは検出されるが対象外）: Spawn/Play 系（VfxManager.SpawnDataLocal・AudioManager.PlaySeData・PresentationManager.PlayLocalInternal）は呼び出しごとに Instance（class）を 1 個 new する既存設計です（PresentationInstance は List×7 + R3 Subject×4 も new します）。Instance プーリングという大きな設計変更が必要なため、対応するテスト（*_RecordsAllocForKnownIssue）は記録するだけで assert しません。新しい Tick/Spawn/Play コードを書くときは、この既知課題を新たな LINQ/クロージャ追加の免罪符にしないでください（既存の allocation を増やさない・可能なら減らす）。

やってよい書き方 / 悪い書き方の対比例:

悪い例（Tick 内）良い例
foreach (var x in list.Where(a => a.IsActive))（LINQ + クロージャ + IEnumerator の alloc）for (int i = 0; i < list.Count; i++) { if (!list[i].IsActive) continue; ... }
list.Sort((a, b) => a.Time.CompareTo(b.Time));（ラムダがクロージャでなくても delegate alloc の懸念があるなら IComparer を再利用する）再利用可能な static readonly IComparer<T> を渡す
Dictionary<int, T> に enum や int をそのまま key にする（value type → object への暗黙 boxing）Dictionary<ulong, T> のように boxing を起こさない key 型を使う、または構造体を直接比較する

例外で止めない設計

D-Drive は「例外で止めず、警告 + no-op / Placeholder で継続する」ことを設計原則にしています（CLAUDE.md §0-4）。ゲームコードを書くときは、これは次のことを意味します。

  • 未登録 ID を Play/Spawn しても例外は飛ばず、警告ログ + Handle<T>.Invalid（または Placeholder 演出）が返る。戻ってきた Handle が Invalid でも、それを使って Stop/IsPlaying 等を呼び続けて構いません（no-op として安全に無視される）
  • Bind 前の静的ファサード（Audio/Vfx/Presentation 等）を呼んでも例外にならず no-op になる（DDriveRuntimeBootstrap が起動する前のコードパスでも壊れない）
  • これに甘えて「戻り値を握りつぶす」のではなく、必要であれば Handle.IsValid やログでデザイナーへの「未登録の発注」を可視化する運用（docs/13_extensions.md の A-1）が推奨されます

Data は読み取り専用

Manager は Data（AssetDataBase 派生の ScriptableObject）を実行時に書き換えません。Instance ごとに変化する現在値（再生位置、現在のマテリアル値など）は Instance 側に持たせます（例: ModelsManager.Materials）。エディタコードが Data を書き換えるときは必ず Undo.RecordObject + EditorUtility.SetDirty を通してください。

Validation と CI の走らせ方

Tools/CI/run-ci.cmd が .github/workflows/ci.yml と同じ検査をローカルで実行します（Unity Editor でこのプロジェクトを開いたままだと多重起動になり失敗するので注意）。

ステップ内容
[1/6]DDrive.Editor.CI.ValidateAll（Validation。Error があれば fail）
[2/6]DDrive.Editor.CI.RegenerateIds（ID 定数再生成）実行後、git diff --exit-code でコミットされていない差分が無いことを確認
[3/6]EditMode テスト
[4/6]PlayMode テスト
[5/6]Performance テスト（DDrive.Tests.Performance、-testCategory Performance、0 alloc 検証。前節参照）
[6/6]NetCheck（Builds\DDriveNetCheck\DDriveNetCheck.exe がビルド済みのときだけ実行。無ければスキップするだけで CI 全体は失敗させない任意ステップ）
[6/6] NetCheck の失敗が従来握りつぶされていました。 run-ci.cmd の if exist ... call "%~dp0run-netcheck.cmd" ブロック内では、バッチファイルの遅延展開の仕様上 %ERRORLEVEL% がブロックに入る前の値（直前の [5/6] Performance の結果）に展開されてしまい、NetCheck 自体の成否が正しく判定されていませんでした（2026-09-17 修正、!ERRORLEVEL! の遅延展開 + NETCHECK_EXIT への退避で修正済み）。修正後の初回実行では、今まで見えていなかった NetCheck の失敗が新たに表面化する可能性があります。[6/6] が FAIL した場合は %RESULTS_DIR%\NetCheck\summary.md を確認してください。

PR チェックリスト

上記はあくまで実用的な抜粋です。Manager/基盤・Data/シリアライズ・Editor/ツールを含む全チェック項目は docs/12_review.md §3 を参照してください。コード PR とデータ PR は分離されており、データ PR は Validation green + プレビュー動画で足ります（コードレビュー不要）。

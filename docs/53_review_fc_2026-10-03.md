## P2 — 直すべき不具合・設計上の穴

### FC-R-01. 【FC-15】右クリックの「MaterialData を作成」は対話的な操作なのに確認が出ず、`Ask` の既定で「保つ」を選んだ既存 Data のシェーダーを `DDrive/Lit` に戻す

- **場所**: `Packages/com.ddrive.core/Editor/Creation/SourceDataCreation.cs:126`（`UnityMaterialMigrator.Migrate(material, category)` = 引数の少ない旧オーバーロード）、`Packages/com.ddrive.core/Editor/Material/UnityMaterialMigrator.cs:78-90`（`explicitHandling == null` → `HandlingFor(profile)` → `Ask` は `Convert`）、同 `:126`（`if (data.Shader != target && !(keepSource && data.Shader != null))`）
- **何が問題か**: FC-15 の対話判定は「呼び出し側が対話的かを渡す」作りだが、`SourceDataCreation`（`AssetContextMenu` の「Material を作成」= デザイナーが右クリックで起こす操作）が旧オーバーロードを呼んでいるため非対話扱いになり、`Ask` は黙って `Convert` になる。さらに `Migrate` は Convert のとき**既存 Data の Shader が `DDrive/Lit` 以外なら上書きする**（`keepSource == false` なので上の条件が真）。
- **失敗の筋書き**: Profile は既定の `Ask`。(1) Model エディタの「元ファイルを再読み込み」でダイアログが出て「元のシェーダーのまま保つ」を選ぶ → Toon の `.mat` から `Shader = TDrive/Toon` の MaterialData ができる。(2) 後日、同じ `.mat` を Project で右クリック →「D-Drive > Material を作成」（既存なら更新の扱い）。ダイアログは出ず、`data.Shader`（Toon）≠ `target`（Lit）なので `Undo.RecordObject` → `data.Shader = Lit` → `Specific = Merge(Specific, Lit)`。Report にログ 1 行が出るだけで、FC-15 が防ぐはずだった「知らないシェーダーが Lit に化ける」罠（doc17 罠 1・docs/51 R-9）がそのまま起きる。`MayaMaterialImporter` 側の既存 Data は `Shader == null` のときしか書かないので、同じ操作でも FBX 内蔵の Material では起きない（経路で挙動が食い違う）。
- **直し方の案**: (a) `SourceDataCreation` の Material 経路を `UnknownShaderGuard.TryResolve(profile, 選択全体の Material, IsInteractiveSession(), out handling)` → `Migrate(..., handling)` にする（1 操作 1 回の確認。キャンセルなら何もしない）。(b) 加えて `Migrate` の「既存 Data のシェーダーを寄せる」条件を、**既存 Data の Shader が「知らないシェーダー」（`UnknownShaderGuard.IsUnknown`）で、呼び出しが非対話の `Ask` のときは上書きしない**ようにする（明示的に `ConvertToLit` / ダイアログで「変換」を選んだときだけ寄せる）。(c) テスト: 「Keep で作った Data を非対話の `Migrate` に通しても Shader が変わらない」を `UnknownShaderPolicyTests` に足す。CHANGELOG の FC-15 の記述（「対話的な操作 = Model エディタの再読み込みと Generate メニュー」）に右クリック作成を含めるか、含めない理由を書く。
- **確度**: 確認済み（コード読み）

### FC-R-02. 【FC-15】シェーダーが欠けた Material（`Hidden/InternalErrorShader`）を「知らないシェーダー」として保ってしまう

- **場所**: `Packages/com.ddrive.core/Editor/Material/UnknownShaderGuard.cs:52-55`（`IsUnknown` = `!IsSupported && !StartsWith("DDrive/")`）、`MayaMaterialImporter.ResolveTargetShader`（`unknownShader == Keep && IsUnknown(source.shader)` → `source.shader`）、`UnityMaterialMigrator.MigrateCore`（同様）
- **何が問題か**: シェーダーのアセットが見つからない `.mat`（パッケージ未導入・GUID 切れ）は、Unity が `material.shader` に `Hidden/InternalErrorShader` を返す（**この Unity の挙動は推定**。一般に知られた挙動だが本レビューでは実行確認していない）。`IsUnknown` はこれも「知らないシェーダー」と判定するので、`KeepSource` / ダイアログで「保つ」だと `MaterialData.Shader = Hidden/InternalErrorShader` が保存され、実行時は常にピンク。ダイアログにも「Hidden/InternalErrorShader（N 件）」と出るだけで、欠けていることが伝わらない。
- **失敗の筋書き**: MS2026 で T-Drive を入れる前に Toon の `.mat` だけが先に入った（よくある順序）→ `UnknownShaderPolicy = KeepSource`（docs/51 §7.2-6 の推奨設定）→ 自動取り込みで `MaterialData.Shader = InternalErrorShader` が保存される → 後で T-Drive を入れても既存 Data の Shader は上書きされない（FC-15 が「既存の有効な Shader は上書きしない」ため）。
- **直し方の案**: `IsUnknown` から `Hidden/InternalErrorShader`（`shader.name == "Hidden/InternalErrorShader"` または `!shader.isSupported` 等）を除き、その Material は「シェーダーが欠けている」として警告 + `DDrive/Lit` に変換する（または Data を作らない）。ダイアログの一覧にも「欠けている」と別行で出す。テストを 1 件足す（シェーダー参照を外した `.mat` は Keep されない）。
- **確度**: 推定（Unity が欠けたシェーダーを `InternalErrorShader` で返すこと）。コード側の判定漏れは確認済み

### FC-R-03. 【FC-4 / 既存】時刻ちょうど 0 秒（= 再生開始位置ちょうど）のマーカーは決して発火しない

- **場所**: `Packages/com.ddrive.core/Runtime/Cutscene/CutsceneManager.cs:268`（`PlayLocalInternal` の `AdvanceMarkers(instance, instance.Elapsed, fire: false)`）、`:716`（`AdvanceExternalMarkers` の `list[cursor].Item1 <= newElapsed`）。Edit Mode は `Editor/Cutscene/CutsceneEditModePreviewProvider.cs:199-203`（再生開始の立ち上がりで `SilentAdvanceTo(elapsed)`）
- **何が問題か**: Play 開始時に「既に過ぎたマーカーを無音で飛ばす」ため `fire: false` で現在位置まで進めるが、比較が `<=` なので `elapsedSeek == 0` のときも**時刻 0 のマーカーが「既に過ぎた」扱いで無音になる**。コメント（`:266-267`「elapsedSeek==0 なら何も跨がない」）と実挙動が食い違っている。既存 4 種（Event / Signal / Shake / Haptic）も同じで、FC-4 はこの規則をそのまま外部マーカーに広げ、E-20 で「Seek / Skip / Late Join で跨いだ分は無音」と契約にした（0 秒の扱いは契約にも docs にも書かれていない）。Edit Mode も再生開始位置ちょうどのマーカーは無音。
- **失敗の筋書き**: T-Drive がショット先頭（フレーム 0）に「このショットの表情を初期化する」`FacialMarker : ICutsceneMarker` を置く → Play でも Edit Mode でも一度も `Fire` されない。テスト（`ExternalContractMarkerTests`）はマーカーを 1.0 / 1.5 / 2.0 / 3.0 秒に置いているので検出されない。
- **直し方の案**: (a) 開始時の無音追い付きを「`elapsedSeek > 0` のときだけ」にし、かつ `fire: false` の比較を `< newElapsed`（開始位置ちょうどは未通過）にする、のどちらかで「開始位置ちょうどのマーカーは最初の Tick で発火」と定義する。既存 4 種の挙動も変わる（0 秒の Event マーカーが鳴り始める）ので、**既存 4 種まで変えるか・外部マーカーだけにするかを決めてから**直し、CHANGELOG の互換性節に書く。(b) どちらにしても E-20 の文面に「開始位置ちょうどのマーカー」の扱いを明記し、テストを足す（Play・Edit Mode・Late Join〔`elapsedSeek` ちょうどの位置〕の 3 つ）。
- **確度**: 確認済み（コード読み。比較演算子と呼び出し順から一意に決まる）

### FC-R-04. 【FC-4】Timeline 直下のマーカー領域（`timeline.markerTrack`）に置いた `ICutsceneMarker` が発火しない可能性

### FC-R-05. 【FC-1 × FC-12】`ApplyBindings` の共有バッファ `_bindingResolved` が再入で壊れ、`Cutscene.Play` から例外が漏れる

- **場所**: `Runtime/Cutscene/CutsceneManager.cs:351-402`（`_bindingResolved.Clear()` → 添字代入 `:374` → パス 2 → `Clear()`）、`Editor/Cutscene/CutsceneEditModeDirectorSetup.cs:213-264`（static の `_bindingResolved`、`:236`）

### FC-R-06. 【FC-11】LightMode タグの無いパス（URP の輪郭線 `SRPDefaultUnlit`）を `DisabledPasses` で止められるか未確認・検査が偽陽性の Warning を出す

- **場所**: `Runtime/Material/MaterialShaderInfo.cs:18-46`（`FindPassTagValue(i, "LightMode")` が空のパスは一覧に入れない）、`Runtime/Material/MaterialDataValidator.cs`（FC-11 節: 一覧に無ければ Warning `DD-MAT-PASS-UNKNOWN`）、`MaterialManager.ApplyPassesAndKeywords`（`SetShaderPassEnabled(name, false)`）
- **何が問題か**: T-Drive の Toon の輪郭線パスは `SRPDefaultUnlit`（T-Drive doc08 §3「Outline（`SRPDefaultUnlit`、Cull Front）」）。URP では LightMode タグを**書かない**パスも `SRPDefaultUnlit` として描かれる。(1) タグを書かないパスは `CollectLightModes` の一覧に出ないので、`DisabledPasses = { "SRPDefaultUnlit" }` に Warning「LightMode にありません（無視されます）」が出る（Material Editor の候補にも出ない）。(2) `Material.SetShaderPassEnabled("SRPDefaultUnlit", false)` がタグ無しのパスを止めるかは Unity の実装次第（**推定**: タグの値で照合するため、タグ無しのパスは止まらない可能性がある）。doc17 §3 #11（輪郭線なし）は FC-11 の主目的の 1 つなので、ここが効かないと T-Drive は生成シェーダーを増やす回避策に戻る。テスト用シェーダー `Tests/Runtime/Shaders/DDriveTestPassKeyword.shader` はタグ付きのパスで検証しており、タグ無しのケースは無い。

- **確度**: 推定（Unity の照合規則）。検査の偽陽性はコード読みで確認済み（タグ無しなら一覧に入らない）

## T-Drive との相性の所見

- **FC-1 + FC-5（Facial トラックの自動追加）**: 形は T-Drive の想定（doc15 §5.5）に合っている。リスナーは「`Timeline` に `FacialCorrectionTrack` を足し、`Data.Bindings` に `SameAsTrack` を追記」すればよく、保存も不要。注意点は 2 つ: (1) **`Roles` は今回の取り込みに含まれた FBX の分だけ**（FC-R-15）。全キャラを対象にするなら `Data.Bindings` / `Timeline.GetOutputTracks()` から役を拾う。(2) リスナーは `DDrive.Tests*` 以外の名前のアセンブリに置く（`Bridges.DDrive.Editor` なら問題なし）。
- **FC-12（`ToonCharacter` / Runner の初期化）**: `OnModelSpawned` はスロット適用・DefaultAnimation 開始の後で、doc17 M-2 の「スロット適用の後に確実に初期化」を満たす。ただし (1) **Edit Mode のプレビュー（Model エディタ・Cutscene の Edit Mode プレビュー）でも `ModelsManager` 経由で呼ばれる**ので、リスナーは `Application.isPlaying == false` でも安全に動く必要がある。(2) Spawn 後にゲームが `Models.SetMaterial` でスロットを差し替えても通知は無い（再配りが要るなら T-Drive 側で `SetMaterial` の後に自分で呼ぶ）。(3) リスナーは**初回 Spawn 時に 1 回だけ集める**ので、実行時に `AddComponent` したものは対象外（Prefab に付けておく）。(4) `OnModelSpawned` の中から Cutscene を再生しない（FC-R-05 が直るまで）。
- **FC-2（返却時の復元）**: 「既定値」は最初の Spawn 時点（Runner の `OnEnable` 後）の値（FC-R-07）。Runner が `OnEnable` で `FC_*` を書いてもそれが既定になるだけで害は無い。Runner は引き続き `IPoolable` を実装しなくてよい（FC-2 で全 `IPoolable` に呼ばれるようにはなった）。
- **FC-4（`FacialMarker`）**: ショット先頭（0 秒）に置いたマーカーは発火しない（FC-R-03）。Timeline 上端のマーカー領域に置いた場合も発火しない可能性がある（FC-R-04、要確認）。直るまでは「トラック上の 0 秒より後に置く」を T-Drive の手順に書いてもらう必要がある。
- **FC-11（Toon の影・輪郭線）**: `ShadowCaster` を止める用途は問題なし。**輪郭線（`SRPDefaultUnlit`）は、T-Drive のシェーダーがパスに `LightMode` タグを明示していないと止まらない / 検査が偽陽性の Warning を出す可能性がある**（FC-R-06）。T-Drive に「輪郭線パスは `Tags { "LightMode" = "SRPDefaultUnlit" }` を明示する」を依頼するのが確実。
- **FC-15（`KeepSource`）**: docs/51 §7.2-6 の推奨（T-Drive を使うプロジェクトは `KeepSource`）は妥当。ただし T-Drive 導入前に Toon の `.mat` が入ると、欠けたシェーダーを保ってしまう（FC-R-02）。導入順を「T-Drive → Toon の素材」にするよう案内するか、FC-R-02 を直す。`Ask` のままだと右クリック作成で Lit に戻る（FC-R-01）。
- **FC-14**: 提供口の形（`GetRules()` / `GetTables()` はドメインリロードごとに 1 回）は T-Drive のブリッジから使いやすい。外部規則は Profile の `T_` 規則より先に効くので、`_ToonMask` のような名前空間付きの接尾辞に限る運用が前提（汎用の接尾辞を返すと MS2026 の既存テクスチャの設定を上書きする）。
- **FC-3**: Runner（実行順 10000）から呼べば契約どおりカット姿勢が返る。分割画面は MS2026 側が `IViewProvider` を書く必要がある（T-Drive では完結しない）。
- **FC-7**: docs/51 §7.1-10 のとおり、T-Drive のクリップが `ScriptableObject` を直接参照していると依存グラフには出ない。T-Drive のデータを D-Drive の「未使用アセット」から守る必要は無い（Data として登録していないため）ので、そのままでよい。

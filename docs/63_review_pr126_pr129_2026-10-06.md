### 確認して問題なしだった観点

- **深さ 8 の整合**: 実行時は Open した CanvasData を `Depth = 1` とし、`node.Depth >= 8` の段では子を処理しない → 埋め込みは最大 7 段。Editor の `CollectWireStages`（`depth < 8` で最大 8 段）と #133 の `CollectEmbedPaths`（`depth >= 8` で打ち切り = 最大 8 段）は**同じ 8 段で互いに一致**し、どちらも実行時より 1 段深いところまで見る。8 段目は実行時に「入れ子が深すぎます」の警告でスキップされる段で、そこまでトリガーを避けたり None の注意を出したりしても安全側（配線を誤って止めることは無い）。実害が無いので指摘にはしない（揃えるなら `UiManager.MaxEmbedDepth` と同じ値の定数を Editor 側で 1 か所に持つ）。
- **入れ子の入れ子で実行時と欄が一致するか**: `HasEmbed` / `CollectEmbedPaths`（[65] GG-R-07）と `CollectWireStages` は、どちらも直下の登録の `RootPath` を結合して内側へ進む形で、実行時の `childPrefix`（`EmbeddedCanvasPaths.Combine(node.Prefix, embed.RootPath)`）と同じパスを作る。`EmbeddedRootPath` の解決（`OptionRoot/Inner`）と欄の選択肢・トリガーの回避は同じ段を見ている。`DescribeProblem` は `EmbeddedRootPath` の未登録の注意が None の注意より先なので、#133 の注意を隠さない。
- **循環**: `CollectWireStages` は `child == current` と「既に集めた段にある」で止めるが、最初の `canvas` 自身は `into` に入らないので、A → B → A では A が 1 回だけ段に入る（3 段目の B で止まる）。実行時は `ChainContains` でその段をスキップする。循環は別途 Validation の対象で、余分に避けるだけの安全側なので問題なし。

#### GE-R-20. 【GE-R-18 の対応】`ReferenceEquals` は、Editor で未割り当ての Object の欄が「偽の null」になる場合に null どうしを「違う」と判定し、空のテクスチャの欄を持つマテリアルの再実行が毎回「更新」になる（推定）

- **場所**: `Editor/Material/UnityMaterialMigrator.cs` の `SameValue`（`case ParamValueType.Object: return ReferenceEquals(a.ObjectValue, b.ObjectValue);`）。呼び出しは `CopySpecificValues`（`value.ObjectValue = source.GetTexture(name)`。空のスロットでは本物の null）
- **細部**: Unity の Editor では、シリアライズされた `UnityEngine.Object` の欄が未割り当てのとき、読み込み後に本物の null ではなく「偽の null」（管理側の外殻で、インスタンス ID は 0、`== null` は true）が入ることがある（`UnassignedReferenceException` を出すための仕組み。MonoBehaviour では確実で、ScriptableObject の構造体配列の中の欄でも同じかは**未確認**）。そうなる場合の筋書きは次のとおり。1 回目の Migrate で Data に null を書く → Editor を再起動するかドメインを再読み込みする → 2 回目の Migrate では `a` = 偽の null、`b` = 本物の null で、`ReferenceEquals` が false になる → 書き込み・`Undo.RecordObject`・`SetDirty`・`Updated 1`。これはテクスチャの欄が空のまま固有の値に入っているたびに起きる（Detail Map など、空のスロットはよくある）ので、GE-R-09（P2）で直した「変えていない .mat の再実行が『更新』に数えられる」が戻る。今のテスト `Migrate_Rerun_CountsUnchanged_UnlessSpecificValuesDiffer` は同じセッションの中で再実行するので、この経路を通らない。
- **直し方の案**: 参照ではなくインスタンス ID で比べる: `static int IdOf(Object o) => ReferenceEquals(o, null) ? 0 : o.GetInstanceID();` → `IdOf(a.ObjectValue) == IdOf(b.ObjectValue)`。この比べ方は、偽の null（0）と本物の null（0）を「同じ」、欠けた参照（0 でない ID が残る）と null を「違う」、生きている同じアセットを「同じ」と判定する。偽の null があってもなくても正しいので、確かめなくても入れられる。`GetInstanceID` は管理側の欄を読むだけで、破棄済みの外殻でも例外にならない。
- **固定するテスト**（EditMode）: 「欠けた参照 → null は更新」: テクスチャを作って Data の固有の値に入れ、`Object.DestroyImmediate` で破棄する（外殻が残り `== null`）→ テクスチャの無い .mat で Migrate → `Updated 1`・値が本物の null。「null どうしは変更なし」は、偽の null を作れないので、インスタンス ID の比較にしたうえでコードを読んで確かめる。
- **確度**: コード読み + Unity の仕様からの**推定**（ScriptableObject の構造体配列の中の欄に偽の null が入るかは、Unity で 1 回確かめれば確定する。手順: Editor を再起動した後、空のスロットを持つ Data で `ReferenceEquals(data.Specific[i].Value.ObjectValue, null)` を見る。true なら P3 に下げてよい）

### 残った指摘（P3、いずれも v1.4.x でよい）

#### GE-R-24. Canvas Editor の「修正」ボタンが `FixAction` の例外を捕まえない（共通の Validator の修正が出るようになったので範囲が広がった）
- **場所**: `CanvasEditorWindow.RefreshValidation` の「修正」ボタン。
- **細部**: これまでの修正は Canvas の Validator のものだけだったが、GE-R-19 で `AssetCreationService.RegisterExisting`（カタログ登録）・Addressables の登録・持ち込み先の Validator の修正も押せるようになった。`DataValidationSection.InvokeFix` は try/catch + `LogWarning` + 再描画だが、Canvas 側は例外がそのまま UI のコールバックの外へ出て、欄が再描画されない（CLAUDE.md §0-4）。また `Undo.RecordObject(_target, …)` は、`_target` 以外を書き換える修正では空の Undo を 1 つ積むだけになる（害は無い）。
- **直し方の案**: `fixAction()` を try/catch で包み、catch でも `RefreshValidation()` する（`InvokeFix` と同じ形）。

#### GE-R-25. GE-R-19 のテストの「CanvasDataValidator / CanvasEmbeddedValidator も走る」の確認が、`-ActiveValidator` の結果だけで通ってしまう
- **場所**: `CanvasEditorValidation_UsesCommonRunner_AndIncludesEmbeddedActiveValidator` の 2 つ目の `Assert`。
- **細部**: `DD-CANVAS-WIRE-EMBED-UNKNOWN` の文言は `ButtonWire[0] '…'` で始まるので、`Contains("ButtonWire")` の OR は 1 つ目の `Assert` と同じ結果で常に満たされる。3 Validator が実行部の対象にあることは「柵」の `CollectionAssert` で固定されているので実害は無い。
- **直し方の案**: 2 つ目の `Assert` を消すか、`CanvasDataValidator` / `CanvasEmbeddedValidator` 固有のコードで確かめる。

#### GE-R-26. CHANGELOG に、Canvas Editor の Validation の欄に共通の Validator が出るようになったことが書かれていない
- **細部**: 3 回目のレビュー（docs・CHANGELOG 節）で「GE-R-19 を直すと 1 文を足す」とした分。Canvas Editor の欄に Addressables 未登録・スキーマ版・セットアップ・持ち込み先の Validator の指摘が新しく出る（見た目の変化）。`CollectValidation` / `TryRemoveWire` / `RemoveOutcome` は `DDrive.Editor` の public で、互換性のスナップショット（`DDrive.Foundation` / `DDrive.Runtime`）の対象外。Run All の結果と重さは変わらないので、互換性節は不要。
- **直し方の案**: v1.4.0 の未リリース節の「ボタンの配線」か Canvas Editor の行に 1 文（「Validation の欄はほかの専用エディタと同じ共通の検査を出す」）。

## 1. 撮る人のチェックリスト

### 1.1 撮る前に

- [ ] [36 §4](36_manual_screenshot_list.md) で、今回撮る番号の「何を映すか」「準備」「撮り方」を読む
- [ ] Unity Editor の **ダークスキン**（既存画像と統一）
- [ ] Windows の**拡大/縮小 100%**（[09 §7.1](09_editor_tools.md) の基準環境と揃える）
- [ ] 撮影対象のウィンドウを**フローティング**にして、[36 §3](36_manual_screenshot_list.md) の幅の目安に合わせる
  - Inspector 系（1 カラム）: 550〜600px
  - タイムライン / ノードグラフ系（Anim / Canvas / Presentation / Anchor Group Editor）: 1200〜1400px
- [ ] 「準備」の列にある状態を作る（練習用データの用意、再生中のタイミングなど）

### 1.2 映してはいけないもの

[35 §0.3](35_tutorial_video_scripts.md) と同じ基準。**ここを外すと取り込む側で伏せ字にする手間が増える**（消せない場合は撮り直しになる）。

- [ ] **Windows のユーザー名**（Inspector の「更新者(Author)」欄・タイトルバー・パス表示・版数表示の `v12・名前・日時` の名前部分）
  → 撮影用の共通アカウント（例: `demo`）で保存し直しておくのが確実
- [ ] **発注ツールの URL・トークン・ログイン中の Google アカウントのメールアドレス**
- [ ] **実在の企画名・チームメンバーの実名・実データ**（練習用のダミー名を使う）

### 1.3 撮り方

- [ ] 対象ウィンドウの領域だけを**範囲指定でキャプチャ**する（フルスクリーンを撮って後から切り出すのではなく、最初から必要な範囲だけ）
- [ ] タスクバー・他アプリを映さない
- [ ] SceneView / Game ビューを含むカットは「エディタウィンドウ + ビュー」を並べたレイアウトで、両方が収まる範囲を切る
- [ ] マウスカーソルは操作対象の直前で止めた位置に置く
- [ ] 形式は **PNG**（透過不要）
- [ ] 下端・右端が**切れていないか**を撮った直後に確認する（2026-09-17 は `root-overview.png` の下端プレビューバーが切れていた）

### 1.4 ファイル名と受け渡し

- [ ] ファイル名は **[36 §4](36_manual_screenshot_list.md) の「ファイル名案」列そのまま**（`images/` は付けず、ファイル名だけ）
  → 番号 `#N` とファイル名の対応が取れていれば、取り込む側は機械的に処理できる
- [ ] 撮れなかった番号は、**番号と理由をテキストで添える**（例:「#27 透明になっている」「#40 不要」）。理由がそのまま [36 §5.4](36_manual_screenshot_list.md) と不具合チケットの根拠になる
- [ ] zip にまとめて渡す（フォルダ階層はあってもよい）

## 2. 取り込む側の手順

以下は 2026-09-17 に実際に通した順。**この順でやると手戻りが出ない。**

### 手順 1: 展開して突き合わせる

```bash
unzip -o <受領.zip> -d <作業用ディレクトリ>
```

- [ ] ファイル名を [36 §4](36_manual_screenshot_list.md) の「ファイル名案」と突き合わせ、**番号 → ファイル名の対応表**を作る
- [ ] **zip に無い番号を列挙する**。撮れなかったと申告された番号と突き合わせ、**申告に無いのに zip にも無いもの**を洗い出して撮影者に確認する
  → 2026-09-17 はこれで #11 / #20 の撮り忘れが見つかった
- [ ] 逆に、リストに無いファイル名が混ざっていないかも見る

### 手順 2: 中身を確認する（撮り直しの判断はここで）

- [ ] **プライバシー**: ユーザー名・URL・トークン・メールアドレス・実名が写っていないか。数枚だけでなく、**該当しそうな画面（Asset Browser の更新者列・仕様書同期・発注ツール）は必ず開いて見る**
- [ ] **見切れ**: 下端・右端が切れていないか
- [ ] **内容の食い違い**: [36 §4](36_manual_screenshot_list.md) の「何を映すか」と実際の画面が合っているか
  → 2026-09-17 は #58 が「詳細パネル」ではなく「新規発注」パネルだった
- [ ] 消せるものは手順 3 で伏せ字にする。消せない・内容が違うものは撮り直しを依頼し、**それ以外は止めずに先へ進める**

### 手順 3: 伏せ字（必要な場合のみ）

Pillow で該当欄を塗ってダミー文字を描く。Pillow が無ければ `python -m pip install pillow`。

```python
from PIL import Image, ImageDraw, ImageFont
im = Image.open(src).convert('RGB')
d = ImageDraw.Draw(im)
f = ImageFont.truetype(r'C:\Windows\Fonts\segoeui.ttf', 12)
for (x0, y0, x1, y1) in [(151, 65, 464, 83)]:          # 塗る矩形
    d.rectangle([x0, y0, x1, y1], fill=(42, 42, 42))   # Unity ダークスキンの入力欄の背景色
    d.text((x0 + 4, (y0 + y1) // 2), 'https://script.google.com/macros/s/XXXXXXXX/exec',
           font=f, fill=(186, 186, 186), anchor='lm')
im.save(dst)
```

- [ ] 矩形の座標は、枠線の色（Unity ダークスキンでは `(13,13,13)`）を走査して機械的に求めると早い
- [ ] 塗った後、その部分を 2 倍に拡大して**自然に見えるか目で確認**する
- [ ] **伏せ字前の原本はリポジトリに入れない**

### 手順 4: 最適化して配置する

Web 版マニュアルは画像を data URI で埋め込むため、1 枚 150KB を目安にする（[36 §3](36_manual_screenshot_list.md)）。UI のスクリーンショットは元の色数が 1〜2 万色程度なので、**256 色パレット化（ディザ無し）でほぼ劣化なく 1/3 前後になる**。

```python
from PIL import Image
import os, shutil
im = Image.open(src).convert('RGB')
im.quantize(colors=256, method=Image.MEDIANCUT, dither=Image.NONE).save(dst, optimize=True)
if os.path.getsize(dst) > os.path.getsize(src):   # 稀に増えるので保険
    shutil.copyfile(src, dst)
```

- [ ] 配置先は `docs/DesignerManual/images/`
- [ ] **撮影取りやめにした番号の画像は配置しない**（受領していても捨てる）
- [ ] 最適化後、1 枚でも 150KB を大きく超えるものがあれば、元画像の解像度が過大でないか見直す
- [ ] 文字のにじみ・階調の破綻が無いか、**大きめの 1 枚を元画像と並べて拡大確認**する

### 手順 5: HTML に `<figure>` を挿入する

各ページには `<!-- screenshot: 36-#N -->` のコメントが入れてある。そこを目印に挿入する。

```html
<figure>
<img src="images/<ファイル名>.png" alt="<何が写っているか>">
<figcaption><読み方の一言></figcaption>
</figure>
```

- [ ] **既に `<figure>` がある番号（撮り直し分）は、画像ファイルを差し替えるだけ**でよい（2026-09-17 は #1 / #3）
- [ ] **コメントが `<table>` や `<ol>` / `<ul>` の内側にある番号に注意**。そのまま挿入すると `<tr>` の間・`<li>` の間に `<figure>` が入って HTML が壊れる。
      **その表・箇条書きを閉じた直後に置く**こと（2026-09-17 の該当: #18 / #29 / #33 / #44 / #46 / #51 / #56 / #57）
- [ ] コメントが `<td>` の中にインラインで書かれている場合は、コメントごと表の外へ移してから挿入する（同 #57）
- [ ] ファイルは **UTF-8 / CRLF**。読み書きはバイト列で行い、改行コードを壊さない
- [ ] `alt` は「何が写っているか」、`figcaption` は「どう読むか」を書く。既存ページの書き方に合わせる

挿入位置の判定は、コメント行より前の `<table>` / `<ol>` / `<ul>` の開閉を数えて、深さが 0 に戻る行を探せば機械的に決まる。

### 手順 6: 撮影しなかった番号を記録する

- [ ] **撮影取りやめ**（不要と判断したもの）: HTML の `<!-- screenshot: 36-#N -->` コメントを**削除**する
- [ ] **未撮影**（不具合・手順不明で撮れなかったもの）: コメントを残し、`<!-- screenshot: 36-#N / 未撮影: 理由 -->` の形に書き換える
      → 原因が直ったときに、どこに何を入れるかが HTML を見れば分かる状態にしておく
- [ ] 不具合が理由のものは、**[39_usability_fixes_2026-09-17.md](39_usability_fixes_2026-09-17.md) に U チケットとして登録**し、[36 §5.4](36_manual_screenshot_list.md) から相互に参照を張る

### 手順 7: 検証する

配置と挿入が終わったら、機械的に確認する。

- [ ] **参照切れが無いか**: 各ページの `<img src="images/...">` が実在するファイルを指しているか
- [ ] **`<figure>` が表・箇条書きの内側に入っていないか**
- [ ] **ブラウザで DOM を見る**: `[...document.querySelectorAll('figure')].map(f => f.parentElement.tagName)` が全部 `BODY` になっていること
      （ローカルファイルを静的スナップショットとして開くと画像自体は読み込まれないが、**構造の確認には十分**）
- [ ] 配置した枚数・合計サイズを記録しておく

### 手順 8: docs を更新する

- [ ] [36](36_manual_screenshot_list.md) の**撮影結果の節**を更新する（§5 の形式: 方針の変更 / 配置済み / 撮影を取りやめ / 未撮影 / 残っている確認事項）
- [ ] §0 の集計、§2 の既存画像の扱いも合わせて直す
- [ ] 撮影方針を変えた場合（2026-09-17 の「Inspector は撮らない」など）は、**なぜそう決めたかを書く**
- [ ] 撮影者に確認したいことは「残っている確認事項」にまとめ、放置しない

### 手順 9: Web 版マニュアルを再生成する

`docs/DesignerManual/*.html` が真実で、GAS 配信用の断片は生成物（[32](32_spec_web.md)）。

```bash
node Tools/SpecWeb/tools/build-manual.js
```

- [ ] 生成物（`Tools/SpecWeb/html/manual/*.html`、`Tools/SpecWeb/src/ManualPages.js`）は**コミットする**
- [ ] 画像は data URI で埋め込まれるため、生成物のサイズが一気に増える。増え方が想定内か見る
- [ ] drift チェック（`Tools/SpecWeb/test/build-manual.test.js`）が通ること
- [ ] **Node が PATH に無い環境でも、VS Code 同梱の Electron を Node として使える**（2026-09-17 に判明）:

```bash
ELECTRON_RUN_AS_NODE=1 "$LOCALAPPDATA/Programs/Microsoft VS Code/Code.exe" Tools/SpecWeb/tools/build-manual.js
```

  同じやり方で SpecWeb のテストも走る（`--test Tools/SpecWeb/test/*.test.js`）。`Tools/SpecWeb/README.md` §8 参照
- [ ] それでも実行できない場合は**「未実行」と明示して残す**（`clasp push` 前に `Tools/SpecWeb/push.ps1` が自動で再生成するため配信自体は壊れないが、drift テストは落ちる）
- [ ] 画像を入れると生成物が一気に増える。**2026-09-17 の 42 枚取り込みで `Tools/SpecWeb/html/manual/` は 2.9MB になった**（data URI なので元画像の約 1.4 倍）。GAS の 1 ファイル上限には遠いが、git の差分は大きくなる

## 3. 落とし穴（2026-09-17 に実際に踏んだもの）

| 症状 | 原因 | 対策 |
|---|---|---|
| `<figure>` が `<tr>` の間に入って表が壊れた | `<!-- screenshot: 36-#N -->` が表・箇条書きの内側に置かれていた | 手順 5 のとおり、閉じタグの直後に置く。挿入後に手順 7 の DOM 確認を必ず通す |
| 挿入位置の判定が全く効かず、全部コメント直後に入った | 位置判定に使う正規表現の `\b` が、スクリプトを書き出す過程で**実際のバックスペース文字（0x08）**になっていた | 生成したスクリプトは実行前に該当行を目視するか、まず 1 ファイルで試して結果を確認する |
| 画像が合計 5.3MB あった | 撮る人に最適化を求めていない（求めるべきでもない） | 手順 4 で取り込む側が一括で縮小する |
| GAS のデプロイ URL が写り込んでいた | 撮影時に伏せ忘れ | 手順 2 で必ず目視。手順 3 で伏せ字にする |
| Inspector の画像を撮ってもらったが結局使わないことになった | 「どの画面を撮るか」の方針が撮影前に固まっていなかった | 方針が変わったら [36](36_manual_screenshot_list.md) に**理由つきで**記録し、次回の撮影リストに反映する |

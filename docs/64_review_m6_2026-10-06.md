- **同じファイルに 2 回走らせても無害**（書き換え後は `m_Script: {fileID: 0}` が D-Drive の型について残らない。テスト `Migration_RewritesReferences_Idempotent_AndKeepsContent` で固定）。

### 2.4 `CLAUDE.md` §0-1（アセットをテキスト編集しない）との関係と代替案

- §0-1 は**人 / エージェントが手で YAML を触る**ことの禁止で、GUID を正しく引いてツールが機械的に 1 行だけ書き換えるのは趣旨に反しない（Unity 自身の API で直せないことが前提）。書き換えは「MonoScript の GUID を AssetDatabase から引く」「型が実在するときだけ」の 2 点で手作業の事故（GUID の打ち間違い）を避けており、方針として受け入れてよい。
- **実装者の「直せない」主張の裏付け**: `ForceReserializeAssets` で `fileID: 0` のまま・`SerializedObject` で `m_Script` を設定すると例外、は docs/11 M-6 (c) の記録だけで、**それを固定するテストは無い**（`LegacyCutsceneTimelineFixtureTests` は書き換え後の往復だけを見る）。仕組みとしては筋が通る（スクリプトの無いオブジェクトはマネージドの実体が無く、Unity からは「破棄済み」に見える = `SerializedObject` が作れない。再シリアライズは読み込んだ内容をそのまま書くだけ）。
- 代替として考えられたもの: (a) Missing のサブアセットを正しい型で作り直して値を移す — 元の値を読む手段が `SerializedObject` しか無く、それが作れないので不可。(b) `EditorUtility.CopySerialized` — 元のオブジェクトがマネージドの実体を持たないので同じ理由で不可。(c) テキストで直した後に `ForceReserializeAssets` で Unity に整形させる — 可能で、識別子を新しい書式（`::`）に揃えられるが、`.playable` の差分が大きくなる（全行の書き直し）ので、差分を `m_Script` の行だけに抑えた今の選択は持ち込み先のレビューのしやすさの点で妥当。**結論: YAML の書き換えは妥当な手段**。足りないのは周辺の安全策（GF-R-01〜04）。

## 3. マイグレーションを実行しなかった場合の挙動

### 3.1 Editor で旧形式のデータが読めなくなるか — **読めなくなる（新たにインポートされた場合）**

- **事実関係**: 実装者の記録（docs/11 M-6 の (a)）が「型を分けたあと、すでにインポート済みの `.playable` は従来どおり読める。**新しくインポートし直した旧形式の `.playable` は、Signal のトラックが `CutsceneSignalTrack` として読めない**」と明記している。テストでも、`LegacyCutsceneTimelineFixtureTests` は旧形式をインポートした直後の読み込みを一度も検査しておらず（書き換えの**後**の `AssertTimelineLoads` だけ）、実装者が書き換え前に読めないのを見て検査を後ろへ回した経緯と整合する。
- **仕組み（推定）**: v1.3.1 の Editor が `m_Script: 0` のオブジェクトを読めていたのは、Unity 6 が「MonoScript を持たない型」に限って `m_EditorClassIdentifier` から型を引くため。分割後は同じ型が MonoScript を持つので、その経路が使われず、スクリプト参照が null のオブジェクトとして読まれる（= Player と同じ状態）。インポート済みのものが読めるのは Library の取り込み結果（読み込み済みのオブジェクト）が残っているから。
- **v1.3.1 では新規インポートでも読めていたか**: 直接の実測記録は無いが、開発リポジトリは worktree（毎回 Library が新しい）で N-8 の Timeline を Editor で開いて「Editor では読める」と記録している（docs/14 §23.1）ので、読めていたと判断する。**よってマイグレーション前提の、Editor の挙動の後退**。
- **持ち込み先で起きる場面**: (1) Library を作り直す・新しく clone する・CI の新しい Library（`.playable` を初回インポート）、(2) `.playable` のファイルが変わって再インポートされる（**git の pull / merge / checkout**）、(3) 「Reimport」・「Reimport All」。**更新した人が manifest の変更と書き換えた `.playable` を同じコミットにしていれば**、他の人は両方を同時に受け取り (1)(2) でも問題は出ない。**manifest だけ先にコミットされた・書き換え前の `.playable` を含むブランチがマージされた**場合に出る。
- 影響は Editor の Timeline ウィンドウでトラック / マーカーが欠けて見える（または「missing」）・Edit Mode のプレビューと Play Mode でもそのトラックが働かない。

### 3.2 Player — 従来どおり読めない

- 変化なし（実装者の実測 (b): 分割だけで再保存なしのビルドは `signal=0`・`referenced script … is missing` で FAIL）。ビルド時に MonoScript は引き直されない。

### 3.3 その状態で Timeline を保存するとデータが失われるか — **未確認（GF-R-02）**

- Unity は、スクリプトが欠けたオブジェクトのシリアライズ済みデータを保持して書き戻すのが基本（シーンの Missing の MonoBehaviour と同じ扱い）なので、**そのまま保存しただけなら `fileID: 0` + 識別子 + 欄の値が残り、後でマイグレーションすれば直る**、というのが推定。
- ただし、(a) Timeline パッケージ側が `m_Tracks` / `m_Markers` の null の参照を整理する経路（トラックの追加・並べ替え・マーカーの移動で一覧を作り直す等）を通ると、**参照が外れてサブアセットが孤立 → 次の保存で消える**可能性がある、(b) デザイナーが「消えたので作り直した」場合に同じ時刻に二重になる、の 2 つは否定できない。どちらもコードからは決められない。
- **マージ前 / タグ前に開発リポジトリで確かめられる**: 旧形式のフィクスチャを新規インポート → Timeline ウィンドウで開き、別のトラックを追加 / 既存のトラックを移動して保存 → マイグレーション → Signal トラック 1 本 + マーカー 5 個が値ごと残っているか。

### GF-R-04. 開いて未保存の Timeline があると、書き換え直後の `SaveAssets` で元に戻る（または未保存の編集が失われる）おそれ

- **場所**: `CutsceneTimelineScriptReferenceMigration.cs:84-92`、`DDriveMigrationRunner.cs:297`（`DDriveAssetSave.SaveAllSuppressed` = `AssetDatabase.SaveAssets()`）
- **何が問題か**: ディスクのファイルを書き換えて `ImportAsset(ForceUpdate)` するが、同じアセットがメモリ上で dirty（Timeline ウィンドウで編集中・未保存）のときの扱いを考えていない。再インポートでメモリ上の内容が捨てられれば未保存の編集が失われ、捨てられずに残れば直後の `SaveAssets` が `fileID: 0` の内容で書き戻して**書き換えが消え、Id は記録済み**になる（GF-R-01 と同じく二度と直らない）。

- **対応**: **対応済み（2026-10-06）**: 書き換え前に、対象のメインアセットが読み込み済みでアセットまたはサブアセットのどれかが dirty なら、そのファイルは書き換えず「保存してからもう一度」と警告する（警告があるので Id は記録されない。再実行で直る）。判定は `IsDirtyProbe`（テスト用に差し替え可能）。Unity が dirty なアセットの再インポートでどう振る舞うかの確認は不要になった（書き換えないため）。テスト: `DirtyOpenTimeline_IsNotRewritten_AndWarns`・`ProbeFalse_RewritesNormally`。更新ウィンドウの「3. マイグレーション」にも「Timeline を開いている場合は先に保存」と表示する。

### Error か Warning か（実装側の相談への回答）

**推奨: Error のままでよい。ただし根拠の書き方を直す（GF-R-12）。**

- §5.8 の本文は「**新しい検査は** Warning として MINOR で追加し、次の MINOR 以降で Error に昇格」で、公開済みの検査に限る書き方ではない。CHANGELOG・Validator のコメント・本書 GF-R-01 の対応欄にある「§5.8 の 2 段階は公開済みの検査が対象」は §5.8 の読み違い。
- 一方で §5.8 には「**緊急（データ破損を招く等）で最初から Error にしたい場合は §5.12 の手続き**（MAJOR ではないが、CHANGELOG + 移行ガイド + 昇格理由）」の但し書きがあり、この検査はそれに当たる: 検出される状態 = **Player ビルドでカットシーンのトラック / マーカーが読み込まれない（かつ新規インポートでは Editor でも読めない）**ことが確定した状態で、Warning では CI を通ってそのまま Player に出る。
- 持ち込み先の CI への影響: 発火するのは「`Assets/` に旧形式の `.playable` がある」ときだけ（カットシーンを使わないプロジェクトでは出ない）。その状態では、更新直後は同じ理由で `CI.MigrateCheck`（`run-ci` で `ValidateAll` の前段）も赤で、**どちらも「更新を適用」1 回で同時に消える**。つまり Error にしても、持ち込み先が新たに踏む手順は増えない（通常の更新手順の範囲）。更新ウィンドウでは Validation（4 段目）がマイグレーション（1 段目）の後に走るので、手順どおりに更新すれば Error は見えない。
- よって「緊急の例外として最初から Error」を §5.8 の但し書きの手続きどおりに記録すればよい（理由・移行ガイド = docs/60 (c) と CHANGELOG の持ち込み先の作業・§5.8 への 1 項目の追記）。

##### GF-R-20. 「全体の指摘を修正」は M-6 以外の全体向けの修正もまとめて実行する（範囲と順序）

- 対象になる `FixAction` は今のところ 4 種: `DD-CUTSCENE-LEGACY-SCRIPT-REF`（`.playable` の書き換え）、`ContentHashCatalogCoverageValidator`（カタログの Addressables 登録・ラベル）、`CatalogAddressCoverageValidator`（Data の Addressables 登録）、`ProjectSetupValidator` の `DD-SETUP-ADDR-NAME-SPACE`（Addressables の既定アセットのリネーム）。前 2 つの Addressables 系は `IsProjectWide` のため今までどの UI からも呼ばれておらず、本 PR で初めて利用者の操作から届くようになった。どれも冪等で、確認ダイアログに一覧が出るので致命的ではないが、次の点がある:
  - **順序**: Addressables 系の修正は `DDriveAssetSave.SaveAllSuppressed()`（= `AssetDatabase.SaveAssets()`）を呼ぶ。報告の順は `DiscoverValidators` の型の列挙順（決まっていない）なので、これが M-6 の修正より先に走ると、開いて未保存の旧形式の Timeline がここで保存され、GF-R-04 の「未保存なので書き換えない」警告が出ないまま書き換えまで進む（保存しても欠けないことは GF-R-02 のテストで確認済みなので、データは失われない）。あわせて、関係のない dirty な Data も版数の更新を抑止したまま保存される（Addressables 系の FixAction の既存の性質。単独の修正ボタンより一括実行のほうが踏みやすい）。
  - **元に戻せない**: どの修正も `Undo` に載らない（ファイルの書き換え・Addressables の登録・アセットのリネーム）。確認ダイアログにマイグレーションのメニューと同じ「元に戻せない。先にコミット / Timeline を保存」の一文が無い。
  - **その他**: Play Mode 中の実行を止めていない。旧形式の `.playable` が多いとメッセージ（全パスを連結）でダイアログが縦に長くなる。
- **直し方の案**: ダイアログに「元に戻せない変更を含む・先にコミット」を足し、`EditorApplication.isPlaying` なら案内して何もしない。順序は `SaveAssets` を呼ばない修正（M-6）を先に回すか、M-6 の Error だけを先に実行する。メッセージはダイアログ用に 1 行に切り詰める（件数だけ）。

##### GF-R-21. GF-R-17 の Ignore の粒度（開発リポジトリでは Fail のほうがよい）

- SetUp の `Assert.Ignore` はクラス全体（14 件）を飛ばす。`Assets/` 全体を数えるのは 4〜5 件（Validator の件数・`Plan` の「無ければ計画に入らない」・`ScanScope_IsAssetsOnly`）だけで、GF-R-13 の `Apply_…WhenAMigrationThrows` や dirty の判定のテストなど、プロジェクトの状態に依存しないものまで Ignore になる。
- CI（`run-ci.cmd`）は `MigrateCheck` → `ValidateAll` をテストの前に走らせるので、旧形式が残っている状態自体はテストより前に赤になり、CI の穴にはならない。ただし普段の検証（MCP からの EditMode 実行）では Ignore は黄色の 1 行で流れやすく、docs/52 4-7 の確認でフィクスチャを `Assets/` に置いたまま走らせると、M-6 の回帰テストが黙って飛ぶ。
- **直し方の案**: `DDriveProjectSettings.instance.IsDevelopmentRepo` のときは `Assert.Fail`（「旧形式の .playable が Assets/ に残っている: …。マイグレーションを適用するか、確認用のコピーを消す」）、持ち込み先では今の Ignore のまま。可能なら Ignore / Fail は `Assets/` 全体を数えるテストだけに絞る。

##### GF-R-22. 新しいメニューが docs/09 のメニュー表・持ち込み先向けガイドに無い

##### GF-R-23. §5.8 の緊急の例外の記録に、§5.12 の承認の記録と条件の一般化が無い

- §5.8 の但し書きは「§5.12 の手続き」を求めており、§5.12 の 1 は「ユーザー承認」。新しい項には理由・影響・移行の記録はあるが、承認を得たことの記録（または「タグ前の人の確認で承認を得る」）が無い。
- 但し書き本体は「緊急（データ破損を招く等）」のままで条件が曖昧。今回の項が満たしている条件（(1) 検出される状態が Player で既に壊れている、(2) 発火はその状態のときだけ、(3) 通常の更新手順の 1 操作で消える、(4) 承認を記録）を但し書きに書いておくと、次に例外を検討する人が今回の項を前例として拡大解釈しにくくなる。
- **直し方の案**: §5.8 の項に「承認: 〔日付・誰〕」（未なら docs/60 のタグ前の確認項目に入れる）。但し書きに上の 4 条件を 1 行で。

##### GF-R-24. 細部

- `ProjectWideValidationFixes.Apply` の「N/M 件実行しました」は「例外なく戻った数」で、M-6 の修正が dirty で書き換えなかった場合も数える（直後の Run All と `FixPaths` の警告で分かるので実害は小さい）。「実行しました」のままでよいが、警告を出した修正の件数も添えると分かりやすい。

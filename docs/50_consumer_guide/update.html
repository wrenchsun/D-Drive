更新方法

最終更新日: 2026-10-04

D-Drive の新しい版が出たときに、このプロジェクトへ取り込む手順です。Tools > D-Drive > Update > 更新ウィンドウ を開いて進めます。所要時間の目安は 8 分（Unity の再コンパイル・テスト実行を除く）。

版の付け方（SemVer）: D-Drive は MAJOR.MINOR.PATCH で版を付けます。MINOR までの更新は既存のゲームコード・データを壊さないことが互換性ポリシーで保証されています。MAJOR の更新だけが「破壊あり」の変更を含み得ます（削除・改名・型変更など）。更新ウィンドウは MAJOR のときだけ赤字で警告します。

1. 更新チェック

  1. 更新ウィンドウの「1. 更新チェック」で「最新の版を確認」ボタンを押す
  2. git ls-remote で公開されているタグを取得し、現在の参照と比較して「最新です」「MINOR の更新があります」「MAJOR の更新があります」のいずれかを表示する
  3. MAJOR の場合は赤字で警告が出る。適用する前に、下記「MAJOR 更新時の移行ガイドの読み方」を先に読む
  4. 取得できたタグの一覧がドロップダウンに新しい順で並ぶ（既定選択は最新）。更新したい版を選ぶ。タグ名は Git に登録されているとおりに使われます
  5. 「最新」として勧めるのは正式版（vX.Y.Z）だけです。v1.5.0-rc.1 のようなプレリリースは一覧に「（プレリリース）」付きで並びますが、自動では勧めません（より新しいプレリリースがあるときは「プレリリース … もあります」と表示されます）。現在の参照がプレリリースのときだけ、プレリリースも最新の候補になります。正式版が無くプレリリースだけのときは「更新先の版」は何も選ばれていません（使うプレリリースを明示的に選びます）。版として読むタグは vX.Y.Z（3 区間）だけです
  6. 認証が必要なリポジトリ（private）の前提: 更新ウィンドウは git の認証の対話（ログイン画面・パスワード入力）を出さずに実行します。資格情報が切れていると、警告（Authentication failed など）で失敗します。その場合は先に端末で git ls-remote <リポジトリの URL> や git fetch を一度実行して資格情報を更新（Git Credential Manager のログイン等）してから、押し直してください。確認中にウィンドウを閉じる・スクリプトの再コンパイルが走ると、実行中の git は止められます
  7. タグの取得は Editor を止めずに行われ、ウィンドウ上部に「確認中…」と「キャンセル」が表示されます

2. manifest.json の版を上げる

  1. 「manifest を選んだ版に更新する」ボタンを押す
  2. 確認ダイアログの後、Packages/manifest.json の com.ddrive.core の #ref（タグ部分）だけが書き換わる。URL・?path=・git+https/git+ssh の形式は変わらない
  3. 差し替え前の値は自動で退避される。間違えて更新した場合は「前の参照に戻す」ボタンでいつでも戻せる（もう一度押すと戻す前の状態に入れ替えられる、簡易 1 段 undo）
  4. Unity の再コンパイルを待ち、コンパイルエラーが無いことを確認する。コンパイルエラーが出た場合は「破壊あり」の変更を踏んでいるので、下記の移行ガイドを確認する

手動で manifest.json を書き換えたり、Package Manager の UI から書き換えたりしても構いません（更新ウィンドウはその補助です）。

3. 版と CHANGELOG を確認する

更新ウィンドウの「2. 版と CHANGELOG」に、現在の版・前回適用した版と、その間の CHANGELOG.md の該当節が表示されます。「破壊あり」の変更が含まれる場合は警告が出るので、先に移行ガイドを確認してください。

4. マイグレーション（プレビュー）を確認する

「3. マイグレーション(プレビュー)」で、データの形式を直す必要がある件数を確認できます。この時点ではまだ何も変更されません（読み取り専用のドライラン）。

5. 更新を適用する

「4. 更新を適用」ボタンを押すと、内部で次の 4 段がこの順に実行されます。

  1. データマイグレーション（古い形式の .asset を新しい形式に直す）
  2. ID/調整値の定数を作り直す（Regenerate Asset IDs / Regenerate Tuning Keys）
  3. アセット管理の登録を揃える（Addressables 登録の同期）
  4. 自動チェックを実行する（Validation > Run All）
途中の段が失敗したらそこで止まります。 それより後の手順・「前回適用した版」の記録更新は行われません。失敗した段のエラー内容を確認してから再実行してください。

全段成功すると、「前回適用した版」が現在の版に更新されます。更新後は「5. テストを有効化する」「6. エージェント向けスキルを更新」も同じウィンドウから操作できます（セットアップウィザードと同じ項目）。

✔ 更新完了の確認ライン: Validation > Run All で Error が 0 件。実機で SE を 1 件再生できる。NGO を使っている場合は Host/Client を両方同じ版で起動し、接続時のバージョン照合でエラーが出ないことを確認する。最後に manifest / lock / 更新で変わった .asset / 生成コードを 1 コミットにまとめる。

D-Drive 以外のパッケージ（T-Drive など）を更新する

更新ウィンドウの先頭の「パッケージ」一覧には、管理対象のパッケージが並びます。1 行目は常に D-Drive で、D-Drive だけを使っている場合は 1 行だけです。行を選ぶと、下の「1. 更新チェック」「2. 版と CHANGELOG」が選んだパッケージのものに切り替わり、「最新の版を確認」「manifest を選んだ版に更新する」「前の参照に戻す」が D-Drive と同じ手順で使えます。「3. マイグレーション」「4. 更新を適用」「5. テスト」「6. スキル」は D-Drive を選んだときだけ表示されます。

パッケージを追加する

  1. 「URL を入力して追加」に git URL を入れて「追加」を押す。例: https://github.com/<owner>/<repo>.git?path=<フォルダ> / git+https://… / ssh://…（末尾の #vX.Y.Z は付けても付けなくてもよい）。manifest.json にあるパッケージ ID も入力できる
  2. すでに manifest.json にあるパッケージなら、管理対象に登録するだけ（manifest.json は変わらない）
  3. まだ無い URL なら、最新の vX.Y.Z（# 以降を付けた場合はそれ）で導入するかを確認するダイアログが出る。「導入する」で Package Manager が導入し、そのまま管理対象に登録される
  4. URL として読めない入力・vX.Y.Z 形式のタグが無い URL・正式版のタグが無い URL（プレリリースだけのとき。#タグ名 を付けて入力すると導入できます）・導入に失敗した場合は、警告が出るだけで何も変わらない
  5. 導入すると、そのパッケージのスクリプトがこの Unity Editor で実行されます。信頼できる提供元のパッケージだけを導入してください（確認ダイアログにも表示されます）

「manifest にある git URL の依存(未登録)」には、まだ登録していない git URL の依存が出ます。「登録」で 1 クリック登録できます（参照が #vX.Y.Z 形式でないものは、最新版を判定できない旨が表示されます）。「登録解除」は管理対象から外すだけで、manifest.json やパッケージは消えません。

更新できるパッケージの条件

  • git タグ vX.Y.Z が、パッケージの package.json の version と一致している
  • パッケージ直下に CHANGELOG.md（Keep a Changelog 形式。各版に ### 互換性 節、破壊は「破壊あり」）がある。無い場合も更新チェックと版上げは使えて、「2. 版と CHANGELOG」に「CHANGELOG.md が見つかりませんでした」と出るだけ

「vX.Y.Z 以降に対応」の確認

パッケージが package.json に ddriveUpdate を書いていると、更新ウィンドウと Validation > Run All が組み合わせを確認します。

宣言意味満たさないとき
requires必須の相手。導入済みで、版が指定以上未導入・古い → エラー表示（Validation では Warning）
compatibleWith任意の相手。導入されている場合だけ、版が指定以上古い → Warning「〜は <相手> vX.Y.Z 以降に対応」（未導入なら何も表示しない）

相手の MAJOR が宣言より大きいときは「CHANGELOG の互換性を確認」という案内（Info）が出ます。確認は次のタイミングで行われます。

  1. 更新ウィンドウを開いたとき・「依存を再検査」を押したとき: 導入済みのパッケージの今の組み合わせ
  2. 版を上げる（または元に戻す）直前: 上げ先の版の package.json を取得して確認し（最大 30 秒。ウィンドウ上部に「確認中…」とキャンセルが出ます。キャンセルすると「事前確認なしで続けるか」を聞かれます）、満たされなくなる場合は確認ダイアログに警告を出す（「それでも更新する」で続行できる）。取得できなかったときは「事前確認できなかった。更新後に確認します」と表示して続行できる。D-Drive の版を上げる・下げるときも、他のパッケージの対応版を割る場合は同じように警告される（D-Drive の版上げでは上げ先の package.json は取得しないので、待ちは入りません）
  3. 版を上げた後: 依存が満たされないときは「前の参照に戻す」が赤く表示される

ddriveUpdate の書き方の規則: 値は X.Y.Z の文字列だけです（範囲指定は読めず、警告になります）。未知のキーや、値が文字列でない項目（将来の拡張用）は無視されます。プレリリース（-rc.1）は比較で無視され、X.Y.Z で比べます。同じリポジトリの複数のパッケージ（例: T-Drive の toon と facial）は、同じタグ vX.Y.Z に揃えてください。片方だけ版を上げようとすると、確認ダイアログに「同じリポジトリの … は … のままです」と案内が出ます。

追加したパッケージの更新後は、「3. 更新後の確認」の「Validation > Run All を実行して確認済みにする」を押してください（D-Drive のような ID・Tuning の再生成やマイグレーションは行いません）。

ロールバック（更新の取りやめ）

状況手順
manifest を書き換えた直後で、まだ「更新を適用」していない更新ウィンドウ「1. 更新チェック」の「前の参照に戻す」を押す
それ以外（「更新を適用」まで実行済み）manifest / lock / 更新で変わった .asset / 生成コードの変更コミットを git revert し、Unity を開き直す

同一メジャーバージョン内の更新であれば、旧フィールドが残っているため旧版でも読めます（新版だけの値は次に保存したときに失われます）。メジャーバージョンをまたぐ更新のロールバックは「更新前のコミットへ戻す」以外の方法を保証しません。

MAJOR 更新時の移行ガイドの読み方

D-Drive の互換性ポリシーでは、公開 API・シリアライズ形式・ID の導出規則などの「互換面」は MINOR/PATCH では壊されません。MAJOR の更新だけが、事前に [Obsolete]・Warning・移行ツールで少なくとも 2 回の MINOR リリースを経て予告されたうえで、破壊的な変更を行います。

  1. 更新ウィンドウ・パッケージ README.md・CHANGELOG.md のいずれかで MAJOR の更新が「破壊あり」と表示されたら、manifest の版を上げる前に Documentation~/migrations/vN.md（このプロジェクトに同梱されている移行ガイド）を読む
  2. 移行ガイドには「対象・症状・手順・ロールバック可否」が書かれている。**対象**（自分のプロジェクトが該当するか）と**症状**（コンパイルエラーになるのか、実行時の挙動が変わるのか）を先に確認する
  3. 手順に沿って、更新前にゲームコード側を直しておけるものは直しておく（[Obsolete] 警告が出ている API は移行ガイドに代替 API が書かれている）
  4. 上記「1〜5」の通常の更新手順を実行する
  5. 更新後、移行ガイドの「確認方法」に沿って動作確認する

移行ガイドが無い、または内容が不十分な場合は、開発リポジトリ（github.com/wrenchsun/D-Drive）へ Issue を立てるか、CHANGELOG.md の該当版の記述を確認してください。

更新チェックリスト

  1. 作業ツリーをクリーンにし、更新用のブランチを切る
  2. 「1. 更新チェック」で「最新の版を確認」→ 対象版までの CHANGELOG.md の「互換性」節を読む。「破壊あり」があれば移行ガイドを先に読む
  3. 「manifest を選んだ版に更新する」を押す
  4. Unity が再コンパイルするのを待ち、コンパイルエラーが無いことを確認する
  5. 「2. 版と CHANGELOG」の表示を確認する
  6. 「3. マイグレーション(プレビュー)」で対象件数を確認する
  7. 「4. 更新を適用」を実行し、途中で失敗せず最後まで完了することを確認する
  8. Validation > Run All で Error が 0 件であることを確認する
  9. EditMode/PlayMode 相当のテスト（このプロジェクトで用意しているもの）を実行する
  10. NGO を使っている場合は、Host/Client を同じ版で起動し、接続時のバージョン照合でエラーが出ないことを確認する
  11. manifest / lock / 更新で変わった .asset / 生成コードを 1 コミットにまとめる
  12. このプロジェクトの CI が green であることを確認する

マイグレーションの書き方

D-Drive のデータ（.asset）のシリアライズ形式を変えるとき、既存のアセットの値を新しい形式へ機械的に移すための仕組みです（docs/42_distribution.md §4.3、P-7 で実装）。実装は Packages/com.ddrive.core/Editor/Migration/。

まず Unity 標準の道具で足りないか確認してください。 フィールドの改名だけなら [FormerlySerializedAs]（コード不要 = マイグレーション不要、MINOR）。クラス名・名前空間の移動だけなら [MovedFrom]。値そのものの変換が要るとき（型変更、複数フィールドの統合等）だけ IDataMigration を書きます。

スキーマ版（SchemaVersion）とは

AssetDataBase.SchemaVersion(int、[HideInInspector])は「今の D-Drive コードが期待するデータ形式の版」を表す単調増加の整数です。AssetDataBase.Version(保存回数、デザイナーの編集履歴表示用)とは**別物**です。

  • VersionStampProcessor(保存フック)が保存の都度、現在のスキーマ版定数 DDriveSchema.Current(Foundation/Data/DDriveSchema.cs)を SchemaVersion へ書き込みます
  • 既存 .asset(このフィールドが無かった頃に保存されたもの)は SchemaVersion == 0 のまま読まれます。これは「1.0.0 以前の形式」を意味します
  • SchemaVersion が古い Data には SchemaVersionValidator(Warning、Code DD-SCHEMA-OUTDATED)が付きます。実際に値を揃えるのは下記の Runner です

IDataMigration の書き方

「Data 1 個の値を変換する」マイグレーションです。IValidator と同じく 登録リストは無く、クラスを書くだけで TypeCache が自動発見します。

namespace DDrive.Editor.Migration
{
    public sealed class MyFieldTypeChangeMigration : IDataMigration
    {
        // 一度公開したら変えない(DDriveProjectSettings.AppliedMigrationIds に記録される)。
        public string Id => "2026-xx-xx-myfield-float-to-valuedef";

        // 対象にする Data の現在の SchemaVersion(この値未満は対象外)。
        public int FromSchema => 1;

        // 適用後に書き込む SchemaVersion(通常は DDriveSchema.Current)。
        public int ToSchema => 2;

        // 型・フィールドの状態で対象を絞り込む。
        public bool AppliesTo(AssetDataBase data) => data is MyData;

        public void Migrate(AssetDataBase data, MigrationContext context)
        {
            var d = (MyData)data;
            d.NewValueDefField = ValueDef.Constant(d.OldFloatField);
            context.Note($"{d.name}: OldFloatField({d.OldFloatField}) -> NewValueDefField");
            // SchemaVersion 自体はここで書かない(Runner がまとめて ToSchema を書く)。
        }
    }
}
旧フィールドは消さないでください。 [HideInInspector] [Obsolete] を付けて次の MAJOR まで残します(docs/42_distribution.md §5.1・§4.3)。同一 MAJOR 内なら、ダウングレードしても旧コードが旧フィールドを読めることが前提です。

IProjectMigration の書き方

AssetDataBase を持たない SO(AssetCatalog・TuningTable・UiLayerSettings 等)への一括処理です。対象ごとの SchemaVersion が無いため、二重適用の防止は DDriveProjectSettings.AppliedMigrationIds に Id が記録済みかどうかで判定します。

public interface IProjectMigration
{
    string Id { get; }
    void Migrate(MigrationContext context);
}

Runner の動かし方

操作メニュー挙動
ドライランTools > D-Drive > Update > マイグレーション(ドライラン)実データは一切変更せず、対象件数と一覧をコンソールに出す(DDriveMigrationRunner.Plan は読み取りのみ)
適用Tools > D-Drive > Update > マイグレーション(適用)Undo.RecordObject → Migrate → SchemaVersion 書き込み → EditorUtility.SetDirty を対象ごとに行い、VersionStampSuppression.Scope() 内で保存する(= 保存回数は進めない)。Ctrl+Z で戻せる
CI-executeMethod DDrive.Editor.CI.MigrateCheck未適用のマイグレーションがあれば exit 1。Tools/CI/run-ci.cmd の [1/7](Validation より前)

適用順は FromSchema の昇順。対象は SchemaVersion < ToSchema && AppliesTo(data) を満たす Data だけです。適用後は SchemaVersion が ToSchema 以上になるため、次回の Plan では自然に対象外になります(二重適用防止に専用のフラグは要りません)。

テストアセンブリ内の実装は自動発見の対象外です。 IValidator の CI.DiscoverValidators() と同じ理由(テスト用のダミー実装が実運用・CI に混ざらないようにするため)で、DDrive.Tests.* アセンブリ内の IDataMigration/IProjectMigration は DDriveMigrationRunner.DiscoverDataMigrations()/DiscoverProjectMigrations()(ひいては CI.MigrateCheck)から除外されます。テストでは DDriveMigrationRunner.Plan(...)/Apply(...) にダミー実装を明示的に渡してください(Tests/Editor/Migration/DDriveMigrationRunnerTests.cs が実例)。

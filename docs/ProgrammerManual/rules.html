コーディング規約・禁止事項

このページは「守らないと CI が赤くなる」規約を実用の観点でまとめたものです。設計原則の背景は 基本概念、PR を出す前の全チェック項目は docs/12_review.md を参照してください。

禁止 API

Assets/DDrive/Editor/Validation/ForbiddenApiScanner.cs が、Assets/DDrive 配下の全 .cs ファイルをテキストパターン一致（正規表現）で走査します。Roslyn Analyzer ではなく簡易的なテキスト走査です。

#禁止パターン（正規表現）代わりに使うもの許可されているファイル
1\bTime\.(time|deltaTime|unscaledDeltaTime|timeAsDouble|unscaledTime)\bITimeSource（docs/02_core_framework.md §9.5）LocalTimeSource.cs / NetworkTimeSource.cs / GameLoopDriver.cs
2\bResources\.Load\bAddressables 経由（IAssetLoader）（例外なし）
3\bAddressables\.Load\w*\bIAssetLoader 経由AddressablesAssetLoader.cs
4\b(?:UnityEngine\.)?Object\.Instantiate\s*\(|(?<![.\w])Instantiate\s*\(PoolService 経由PoolService.cs / PreviewService.cs（非破壊ループ試聴用の ScriptableObject コピーを許可）
5\bAudioSource\.Play\bAudioManager 経由（例外なし）

いずれのルールも ForbiddenApiScanner.cs 自身は常に例外扱いです（このファイルの Message 文字列がパターンに一致してしまうため、自己検出を避ける自己参照の除外）。// で始まる行（コメント）はどのルールも対象外です。

スキャナは Samples/ フォルダを走査対象外にしています。 Assets/DDrive/Samples/ 配下（NetBridgeSmokeTest.cs 等の手動確認用デモ）はパスに /Samples/ を含む場合、ルールに関係なく丸ごとスキップされます。
ゲームコード（Assembly-CSharp 等）はこのスキャナの対象外です。 Editor/Validation/CI.cs は ForbiddenApiScanner.Scan("Assets/DDrive") という固定パスでしか呼んでおらず、D-Drive 本体以外のフォルダは走査しません。それでも CLAUDE.md §0-3 は同じ禁止事項（Instantiate / Resources.Load / AudioSource.Play の直接呼び出し）をゲームコードにも適用すると定めています。ゲームコードでこれらの API を直接呼んでも CI は検出しません。人が守るしかないことを理解したうえでレビューしてください。

定常経路（Tick / Spawn / Play）でのパフォーマンス規約

毎フレーム、または高頻度に呼ばれる経路（Tick / Spawn / Play）では LINQ・クロージャ・boxing を禁止します（docs/12_review.md §3）。

2026-09-15（6-2）から自動検証があります。 Assets/DDrive/Tests/Performance/（asmdef DDrive.Tests.Performance、com.unity.test-framework.performance 使用）が、Pool の Rent/Return・Vfx/Se/CameraFx/Haptics の Tick・Presentation の Tick+Signal・GameLoopDriver の 1 フレームなど、Tick 系の定常経路を GC.GetAllocatedBytesForCurrentThread() の差分で hard assert します。-testCategory Performance で実行します（Unity Test Runner、または Tools/CI/run-ci.cmd の [5/6]）。GitHub Actions での自動実行は P7 末の CI 導入まで保留されているため、現状はローカル実行が唯一の実行経路です。

既知の未解決 alloc（このチェックでは検出されるが対象外）: Spawn/Play 系（VfxManager.SpawnDataLocal・AudioManager.PlaySeData・PresentationManager.PlayLocalInternal）は呼び出しごとに Instance（class）を 1 個 new する既存設計です（PresentationInstance は List×7 + R3 Subject×4 も new します）。Instance プーリングという大きな設計変更が必要なため、対応するテスト（*_RecordsAllocForKnownIssue）は記録するだけで assert しません。新しい Tick/Spawn/Play コードを書くときは、この既知課題を新たな LINQ/クロージャ追加の免罪符にしないでください（既存の allocation を増やさない・可能なら減らす）。

やってよい書き方 / 悪い書き方の対比例:

悪い例（Tick 内）良い例
foreach (var x in list.Where(a => a.IsActive))（LINQ + クロージャ + IEnumerator の alloc）for (int i = 0; i < list.Count; i++) { if (!list[i].IsActive) continue; ... }
list.Sort((a, b) => a.Time.CompareTo(b.Time));（ラムダがクロージャでなくても delegate alloc の懸念があるなら IComparer を再利用する）再利用可能な static readonly IComparer<T> を渡す
Dictionary<int, T> に enum や int をそのまま key にする（value type → object への暗黙 boxing）Dictionary<ulong, T> のように boxing を起こさない key 型を使う、または構造体を直接比較する

例外で止めない設計

D-Drive は「例外で止めず、警告 + no-op / Placeholder で継続する」ことを設計原則にしています（CLAUDE.md §0-4）。ゲームコードを書くときは、これは次のことを意味します。

  • 未登録 ID を Play/Spawn しても例外は飛ばず、警告ログ + Handle<T>.Invalid（または Placeholder 演出）が返る。戻ってきた Handle が Invalid でも、それを使って Stop/IsPlaying 等を呼び続けて構いません（no-op として安全に無視される）
  • Bind 前の静的ファサード（Audio/Vfx/Presentation 等）を呼んでも例外にならず no-op になる（DDriveRuntimeBootstrap が起動する前のコードパスでも壊れない）
  • これに甘えて「戻り値を握りつぶす」のではなく、必要であれば Handle.IsValid やログでデザイナーへの「未登録の発注」を可視化する運用（docs/13_extensions.md の A-1）が推奨されます

Data は読み取り専用

Manager は Data（AssetDataBase 派生の ScriptableObject）を実行時に書き換えません。Instance ごとに変化する現在値（再生位置、現在のマテリアル値など）は Instance 側に持たせます（例: ModelsManager.Materials）。エディタコードが Data を書き換えるときは必ず Undo.RecordObject + EditorUtility.SetDirty を通してください。

Cutscene（Timeline カットシーン）と共存するためのゲーム側の責務

2026-09-18 に決めた契約です(設計書 docs/26_timeline.md §4.5.1 / §4.6.5。Timeline チケット 6-10a〜d で実装完了、CameraExecutionOrderValidator による検出 1 も 6-10d で実装済みです)。 Maya で作ったカメラワークをゲームカメラに滑らかに繋ぐため、D-Drive はカットシーン再生中にゲームのメインカメラ(Camera.main)の姿勢をゲーム側の書き込みの後から上書きします。この上書きが成り立つ条件と、入力ロックの分担を、持ち込み先のゲームコードが守る契約として先に決めました(MS2026 のカメラ制御はこの契約に合わせて設計します)。

1. ゲームカメラ制御の実行順（契約）

D-Drive 側は DDriveCutsceneCameraApplier（初回再生時に Camera.main へ自動で付く小さな MonoBehaviour）が LateUpdate でカメラの Transform・画角を書きます。この実行順は次のとおりです。

[DefaultExecutionOrder(DDriveCutsceneCameraApplier.ExecutionOrder)] // ExecutionOrder = 1000 public sealed class DDriveCutsceneCameraApplier : MonoBehaviour

DDriveRuntimeBootstrap の -1000（誰よりも先に組み立てる）と対称に、+1000（誰よりも後にカメラを書く）を D-Drive が占めます。ゲームコードの実行順は −1000 より大きく 1000 より小さい範囲に収めてください。 「D-Drive より前」を明示したいときは数値を直書きせず DDriveCutsceneCameraApplier.ExecutionOrder - 1 のように定数を参照してください。カットシーンが再生されていないフレームでは Applier は何もしません（付いているだけではゲームカメラに影響しません）。

#ゲーム側が守る条件理由
G-1Camera.main の Transform・fieldOfView・物理カメラ値への書き込みは Update / FixedUpdate / LateUpdate のいずれかで行う。LateUpdate の場合、そのスクリプトの実行順は 1000 未満（DefaultExecutionOrder 属性も、ProjectSettings > Script Execution Order の設定も）Applier（1000）が同じフレームの LateUpdate の最後に「ゲームカメラの姿勢」を読んでから上書きするため
G-2LateUpdate より後で姿勢を書かない: PlayerLoop の PostLateUpdate 以降に挿した独自システム、Application.onBeforeRender、RenderPipelineManager.beginFrameRendering / beginCameraRendering、Camera.onPreCull 等の描画コールバック内でカメラを動かさない。yield return new WaitForEndOfFrame() からの書き込みも避ける（絵は潰さないが次フレームの「ゲームカメラの姿勢」を汚す）いずれも Applier の後に走り、D-Drive の書き込みを潰す
G-3Cinemachine を使う場合、CinemachineBrain の Update Method は LateUpdate / SmartUpdate / FixedUpdate のいずれか（既定のまま）で、Brain の実行順も 1000 未満Brain は LateUpdate で書くので G-1 と同じ扱い。専用アダプタは v1 では作らず、この契約だけで共存する
G-4（推奨）ゲームカメラ制御は自前の状態（追従目標・前フレームの自分の計算値）から毎フレーム姿勢を計算し、Camera.main.transform の現在値を「前フレームの自分の姿勢」として読み戻さない再生中はカメラに D-Drive がブレンド結果を書いているため、読み戻す実装だとゲームカメラが D-Drive の書き込みに引きずられる（破綻はしないが、終了後にカメラが本来の位置へもう一度動く）
G-5カットシーン再生中に Camera.main を差し替えない差し替えると Applier は新しいカメラへ付け直し、その回の再生はブレンドアウト無しで終わる（警告 1 回）
守られなかったときに起きること: 実行順 1000 以上の LateUpdate や描画コールバックでカメラを毎フレーム書いていると、カットシーンのカメラが一切効かず（キャラ・SE・VFX だけ再生され、ゲームカメラのまま。被写界深度だけ変わる不自然な絵になる）、間欠的に書いているとカメラがカクつく / 震える状態になります。どちらも例外は出ません。そのため次の検出手段を用意します。
検出何が出るか
Validation > Run All（CameraExecutionOrderValidator、CI の ValidateAll にも載る）プロジェクト内の全ランタイムスクリプトの実効実行順（ProjectSettings の値 > DefaultExecutionOrder 属性）を調べ、D-Drive 以外で 1000 以上のスクリプトがあれば Warning、Applier 自身が 1000 でなければ Error。PlayerLoop.SetPlayerLoop / PostLateUpdate / onBeforeRender / beginCameraRendering 等を含む .cs ファイルは Info（カメラを書いていないか人が確認する）
実行時（Editor と Development Build のみ）Applier がカメラの描画直後（RenderPipelineManager.endCameraRendering）に「このフレームに自分が書いた姿勢」と「描画に使われた姿勢」を比べ、違っていれば再生 1 回につき警告ログ 1 回（上書きされたフレーム数 / 総フレーム数、G-1・G-2 の確認と Validation の実行を促す文言）。Applier の LateUpdate が再生中に呼ばれなかった場合（無効化・カメラ消失・差し替え）も警告 1 回。製品ビルドでは検出コードは動きません

2. 入力ロック（LockInput）はゲーム側が止める

CutsceneData には「再生中はプレイヤー入力を止める」フラグ（LockInput）がありますが、D-Drive は「ロック中かどうか」を公開・通知するだけで、実際に入力を止める処理は持ちません。入力系（Input System の Action Map 切替、Host 権威での入力破棄、UI のフォーカス制御）はゲームごとに違うためです。ゲーム側が次のいずれかを購読して止めてください。

公開面型意味
Cutscene.IsInputLockedstatic boolLockInput なカットシーンが 1 つでも再生中か
Cutscene.OnInputLockChangedstatic Observable<bool>（R3）ロック数が 0→1 になったとき true、1→0 になったとき false を 1 回ずつ流す（PauseService.OnPauseChanged と同じエッジ通知。2 本重ねても中間では発火しない）。通常はこれを購読する
CutsceneHandle.IsInputLockedboolその Handle が LockInput かつ再生中か。ブレンドアウト中（Skip / Cancel 後の戻し区間）も true のまま。無効な Handle は false
EventBus（データ側）EventTrigger.Custom キー cutscene/input_lock / cutscene/input_unlockデザイナーが CutsceneData の Events に「ロック開始で字幕 Canvas を開く」等を Data だけで足すためのもの。ゲームコードはこちらを使う必要はありません
// MS2026 側の例: ロック中は Player の Action Map を無効化する
Cutscene.OnInputLockChanged
    .Subscribe(locked => { if (locked) inputActions.Player.Disable(); else inputActions.Player.Enable(); })
    .AddTo(this);

ロックは Cancel / 再生終了で必ず解除されます（Handle の破棄経路は 1 本）。Flags.Pause でポーズ中もロック状態は変わりません。ネット同期再生（Flags.Net = Cosmetic）では各クライアントが自分のロック状態を持ち、Host 権威のゲームロジックが「ロック中のクライアントからの入力を捨てる」かどうかはゲーム側の実装です。

Validation と CI の走らせ方

Tools/CI/run-ci.cmd が .github/workflows/ci.yml と同じ検査をローカルで実行します（Unity Editor でこのプロジェクトを開いたままだと多重起動になり失敗するので注意）。

ステップ内容
[1/6]DDrive.Editor.CI.ValidateAll（Validation。Error があれば fail）
[2/6]DDrive.Editor.CI.RegenerateIds（ID 定数再生成）実行後、git diff --exit-code でコミットされていない差分が無いことを確認
[3/6]EditMode テスト
[4/6]PlayMode テスト
[5/6]Performance テスト（DDrive.Tests.Performance、-testCategory Performance、0 alloc 検証。前節参照）
[6/6]NetCheck（Builds\DDriveNetCheck\DDriveNetCheck.exe がビルド済みのときだけ実行。無ければスキップするだけで CI 全体は失敗させない任意ステップ）
[6/6] NetCheck が FAIL したとき: %RESULTS_DIR%\NetCheck\summary.md を確認してください。

互換性スナップショット（Assets/DDrive/Tests/Editor/Compat/、EditMode テスト）は、公開 API・シリアライズ形式・enum・ID/Address/定数名・ネットメッセージ・生成コード・Validator の重さ・Editor 契約・版番号が意図せず変わっていないかをゴールデン比較で機械的に検出します。P チケット（移植・更新・互換性、docs/42_distribution.md）が完了して互換性ポリシーが発効した後は、このスナップショットが赤い PR はマージしません。意図した変更（追加は MINOR、削除・変更は MAJOR で手続きが必要）なら、Tools > D-Drive > Compat > スナップショットを更新（または一部は環境変数 DDRIVE_UPDATE_COMPAT_SNAPSHOTS=1）でゴールデンを更新し、同じ PR で CHANGELOG.md の互換性節に記載してください（詳細は docs/12_review.md §3 / docs/42_distribution.md §5.11）。

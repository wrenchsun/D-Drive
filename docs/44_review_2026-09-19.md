## P2 — エッジケース / 規約違反 / パフォーマンス

### net

**P2-1. `NgoNetBridge.OnPongMsgReceived` に送信元検証が無い（`4cfa1a2` が `CatalogContentHashResultMsg` に対して塞いだのとまったく同じ穴が `NetPongMsg` に残っている）**

`Assets/DDrive/Runtime/Net/NgoNetBridge.cs:287-294`（`6315ae8` 時点。`senderId` を一切見ずに `_appRoundTripTracker.OnPongReceived(measuredMs)` を呼ぶ）。

`NetPongMsg` は `OnNetworkSpawn`（`:144`）で `Subscribe` されるため `_keyToType` に登録済みになる。`RequestBroadcastRpc`（`:554-572`）は「型登録済みなら」Client からの中継依頼を通す（レート制限 60/秒はあるが型の絞り込みは無い）ので、改造 Client が `Broadcast(new NetPongMsg{...})` すると Host が全員へ中継し、他 Client と Host がこれを受け取る。結果:

- 受け取った Client の `AppRoundTripMs` が任意の値に化け、`_consecutiveMissedPongCount` が 0 に戻るため **`IsAppRoundTripMsStale`（途絶疑い）を任意のタイミングで消せる**
- 本来 `null` のはずの **Host 側でも `AppRoundTripMs` に値が入る**（`NgoNetBridge.cs:105-107` のコメント「Host 自身は計測しない = 常に null」と矛盾）

**P1 にしなかった理由**: 影響が `NetDebugOverlay` の表示と `NetCheckRunner` のログ（`rtt_app_ms` / `rtt_app_stale`）に限られ、ゲームプレイの権威には影響しない。ただし **docs/29 の実機確認はこの 2 つの値を判定基準にしている**ので、「確認の証拠を偽装できる」という意味では無視できない。

**直し方**: `CatalogContentHashGate.HostClientId`（`4cfa1a2` で導入）と同じく、`OnPongMsgReceived` の先頭で `senderId != NetworkManager.ServerClientId` を弾く。ついでに `OnPingMsgReceived`（`:276-285`）は Host だけが応答する作りなので変更不要。

**P2-6. `EditorAnchorRegistry.Refresh` は追加・上書きしかせず、削除されたアセットを Registry から外さない。`88d9989` で「再生のたびに Refresh」にしたことで、この非対称が表面化しやすくなった**

`Editor/Preview/EditorAnchorRegistry.cs:43-99` と `Foundation/Registry/AssetRegistry.cs:36-64, 114-124`。

`Refresh` は生きているアセットだけを `entries` に積んで `RegisterCatalogAsync` に渡す。`RegisterCatalogAsync` は `_index[entry.Id] = entry` で**上書きするだけ**で、消えた Id のエントリも `_byType` の重複も掃除しない。`_loaded`（`AssetRegistry.cs:19`）に至っては `ResolveAsync` が足す一方で、外す経路が存在しない。

その結果、Anim Editor / Presentation Editor を開いたまま Data を削除して「▶ 再生」を押すと、`ResolveOrPlaceholder`（`AssetRegistry.cs:114-124`）は `_loaded` にある**破棄済み ScriptableObject**（C# 参照は非 null なので `is T` が成立する）をそのまま返す。FR-1.4 の「未登録は Placeholder」に落ちず、参照先を触った時点で `MissingReferenceException` になる。

`88d9989` は「ウィンドウを開いた後に**作った**アセットを次の再生から反映する」ことを目的としており（`AnimEditorWindow.cs:781-783`、`PresentationEditorWindow.Preview.cs:230-231`）、**削除は反映されない**。ユーザーからは「再生のたびに最新化される」ように見えるので、期待とのズレが生まれる。

**直し方**: `Refresh` の先頭で「今回集めた Id の集合に無い `_index` / `_byType` / `_loaded` エントリを落とす」か、`AssetRegistry` に `UnregisterMissing(IReadOnlyCollection<ulong> alive)` を足す。あわせて `ResolveOrPlaceholder` / `TryResolveSync` の `cached is T typed` を `cached != null && cached is T`（Unity の `==` オーバーロード経由）にすると、破棄済みを掴んだときも Placeholder に落ちる。

**P2-7. `CatalogAddressCoverageValidator` が「カタログエントリ数 × Addressables 全エントリ数」の総当たりになっている**

**P2-8. `MaterialDataValidator` / `VfxDataValidator` の Warning 文言が「ライティング無し」と断定しているが、判定はそれを保証していない**

`Runtime/Material/MaterialDataValidator.cs:30-38`（「ライティング無しのため {active} でも描画はされますが」）、`Runtime/Vfx/VfxDataValidator.cs:89-104`（「ライティング無しの単純なパスのため」）。いずれも `88d9989`。

判定の実体は `ShaderPipelineAnalyzer.HasSrpDefaultUnlitPass`（`Runtime/Material/ShaderPipelineAnalyzer.cs:101-124`）で、「**いずれかの** SubShader の **いずれかの** パスに `LightMode` タグが無い、または `SRPDefaultUnlit`」という条件でしかない。ライティングパスと非ライティングパスを両方持つシェーダーでも true になるし、`Detect` が `HighDefinition` / `Custom` を返したシェーダー（HDRP 用シェーダーを URP プロジェクトで使った場合など）にもこの文言が出る（前半は `DisplayName(Detect(...))` で正しく「HDRP 用」と出るので、「HDRP 用です。ライティング無しのため URP でも描画はされます」という自己矛盾した文になる）。

**直し方**: 文言を「`LightMode` タグの無いパス（URP の `SRPDefaultUnlit`）を持つため描画される見込みですが」程度に弱める。判定側は最初の SubShader だけを見るか、少なくとも「SubShader 0 に該当パスがあるか」を優先する。

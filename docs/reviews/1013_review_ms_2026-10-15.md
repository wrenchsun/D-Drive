## 総評

- **互換性は「追加のみ」で問題なし**。`public-api-DDrive.Runtime.txt` は 2 コミット合計 `+18 / −0`（MS-1 = `Ui` / `UiManager` のメソッド 5 つずつ、MS-2 = `Cutscene` / `CutsceneManager` のオーバーロード 2 つずつ + `CutscenePlayOptions` 型）。既存の `Open` / `Popup` / `Close` / `Play(id, ctx)` / `PlayData(data, ctx)` のシグネチャは不変で、新しいオーバーロードに既定引数が無いため呼び出しの曖昧さも生じない。シリアライズ形式・enum・ネットメッセージ（`CutscenePlayMsg`）に差分なし。CHANGELOG `[Unreleased]` の追加 / 互換性節もある。

### MS-1

- **後始末**: `Close` → `FinalizeClose`（Pooled = `_pool.Return` → `DestroyOffscreenRoot` で Prefab を `_root` へ逃がしてから専用ルートを破棄、非 Pool = `_pool.Discard`、Placeholder = 破棄）。`PoolService.ForceReturn` は親を変えないので、逃がさないとルートと一緒に破棄される — 逃がしている。`_root` が null（`DestroyEditorRoot` 後）なら Prefab ごと破棄されるが、`PoolService.Rent` は死んだ候補を捨てるので二重貸出・例外にならない。`StopAll`（= `OnSceneUnload`）は `_offscreen` を後ろから `StopAllElementFx` + `FinalizeClose`。Play 中の専用ルートは `DontDestroyOnLoad` なのでシーン切替で先に消えることはない。
- **プールへ返した Prefab に残る状態**: alpha / localScale / anchoredPosition は既存の中立化で戻る。親は `_root` に移るが、次の `Rent` で通常の `Open`（レイヤールート）/ `OpenInto`（専用 Canvas）のどちらでも付け替えられる。`innerCanvas.overrideSorting` / `sortingOrder` は通常の Open と同じ値。CanvasScaler は専用 Canvas 側に写すだけで Prefab 側を触らない（MS-R-01 の対処で `CanvasGroup` を触るなら `FinalizeClose` で戻すこと）。
- **`_offscreen` の Tick 走査**: `for` の後ろから、`TryGet` + `TickElementFx`。LINQ / クロージャ / boxing なし。`FinalizeClose` 内の `_offscreen.Remove` は後ろからの走査なので添字がずれない（同フレームに別の Canvas が連鎖して閉じる場合の危うさは `_stack` の既存ループと同じ）。`gateChanged` を捨てているのは、Offscreen が `RecomputeBlocking` の対象外なので正しい。
- **`PlayDisappear` → `Close` で Disappear が二重に鳴らない**: `StartDisappear` は `DisappearStarted` を見て再生も SE も繰り返さない。`PlayDisappear` 中（非 Closing）の Tick は `DisappearStarted` の要素を飛ばすので `DisappearDone` は立たないが、`Close` の `StartAllDisappearFx` が `PendingDisappearCount = 0` から数え直し、再生中なら +1、終わっていれば `DisappearDone = true` にするので、`PendingDisappearCount` は Close 時点の実態と一致する。Close 前に Disappear が終わっていれば CloseTransition だけで閉じる（テスト (d) のとおり）。
- **`PlayDisappearAsync`**: `ReferenceEquals(inst, instance)` で Handle の再利用を見ており、閉じられたら抜ける。`_tweens` が null でも即完了。
- **`size` の丸め**: 0 / 負なら RT 全面、超過分だけ `Mathf.Min` で丸め、警告は `_offscreenSizeWarned` で Manager ごとに 1 回。`pixelRect` は `targetTexture` 代入の後に設定しているので RT の寸法に対して解釈される。
- **`target` が null / 破棄済み**: `target == null`（Unity の null 判定）で警告 + Invalid。例外にならない。`OpenIntoAsync` も Invalid をそのまま返す（`AwaitOpenTransition` は該当なしで即抜ける）。
- **URP**: `UniversalAdditionalCameraData` を新しい Camera に 1 個だけ付けて `Base` / `renderPostProcessing = false`。`DDrive.Runtime` の asmdef は既に `Unity.RenderPipelines.Universal.Runtime` を参照している（依存の追加ではない）。追加の設定は MS-R-04。
- **隔離**: 専用 Camera は `Untagged` なので `Camera.main` を変えない。AudioListener も付けない。正射影の高さ 10 単位に対して隣のルートとの間隔 100 単位で、Offscreen 同士が互いに映り込まない（横長の RT でも広がるのは X 方向）。
- **しないもの**: `_stack` / `ApplyNavigation` / `ApplyFirstSelected` / modal / `PauseGameWhileOpen`（警告 1 回）/ `HasOpenInLayer`（C-1 のレイヤー共有 CanvasScaler に影響しない）/ `SetLayerVisible` / `CanSelectInto`（`_stack` の先頭しか見ない）はいずれも Offscreen を数えない。`GetContextTransform` は Offscreen も探すので Events の SE / VFX の発火位置は解決できる。
- **例外で止めない / Data 読み取り専用**: 新しい経路に throw は無く、`CanvasData` を書き換えていない。
- **docs**: [07] A-3 の 2026-10-15 の節・ProgrammerManual `ui-api.html`・CHANGELOG はコードと一致（MS-R-01 の「入力を受けない」と MS-R-02 の「n = 呼び出しの連番」を除く）。

### MS-2

- **既定経路の不変**: `options` 既定（`Camera = null`）では `CameraSpecified = false` → `ResolveCutsceneCamera` = `Camera.main`。所有者 1 本・同じカメラの 2 本目は警告 1 回（`_multiCameraWarned`、Data ごと）で無視、の挙動は `Camera.main` 1 台しか無い既定経路では旧実装（全体で 1 本）と同じ結果になる。G-5（`Camera.main` が null / 差し替わり）は「スロットを持つなら `slot.Cam != cam`」で旧 `_cameraOwnerCamera` の比較と同じ判定。`Camera.main` が最初から無いときもスロットを作らず G-5 で終える（旧と同じ）。区間外（`!hasData`）での手放し・`CancelInternal` / `Complete` での手放しも `FindSlotOwnedBy` で漏れなく `ReleaseSlot` → `Restore()` に置き換わっている。旧実装の `_cameraApplier?.Restore()`（`UnityEngine.Object` に `?.`）は破棄済みの Applier でも `Restore` 本体に入り、中で Camera / Volume に触れると MissingReferenceException になりえた（推定）が、新実装は `!= null`（Unity の null 判定）なのでむしろ安全になった。
- **指定カメラの破棄**: `CameraSpecified = true` で `OptionsCamera` が破棄済みなら `ResolveCutsceneCamera` は null を返し、`Camera.main` へ乗り換えない。G-5 で `CameraOwnershipEnded`、破棄済み Applier の `Restore` は呼ばない。他の本・Cutscene 本体は続く（テスト (c)）。`MainCamera` バインドも同じ解決を通る（テスト (e)）。
- **`IgnoreInputLock`**: `AcquireInputLockIfNeeded` が数えず `LockCounted` も立たないので、`ReleaseInputLockIfNeeded` と `_lockDepth`・`IsInputLockedAny`・`OnInputLockChanged`・`cutscene/input_lock` イベントの整合が保たれる。`IsInputLocked(handle)` も `!IgnoreInputLock` を見る。受信経路は既定（false）。
- **ネット**: `CutscenePlayMsg` に options を足していない（`NetMessage` スナップショット不変）。受信側の再生は従来の引数のまま（MS-R-05 は記述と設計上の注意の問題）。
- **`ViewCamera`**: 差分なし。`Camera.main` の Applier の `IsDriving` だけを見るので、指定カメラの再生中は `Source = MainCamera` のまま（[26] §4.6.6 の記述どおり）。
- **Edit Mode プレビュー / `CameraExecutionOrderValidator` / `CutscenePreviewHarness`**: 差分なし（チケットの「やらないこと」どおり）。
- **`CutscenePlayOptions`**: `readonly struct`、1 型 1 ファイル（`CutscenePlayOptions.cs` + `.meta`、短い形、GUID 新規）。アセットになる型ではないので M-6 の規則の対象外。`in` 渡しで boxing なし。
- **docs**: [26] §4.6.6・ProgrammerManual `rules.html` §3・CHANGELOG はネットの記述（MS-R-05）を除きコードと一致。

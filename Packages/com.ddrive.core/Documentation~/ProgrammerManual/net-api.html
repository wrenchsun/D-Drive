ネットワーク（INetBridge / NGO）

D-Drive のアセットシステム本体はトランスポート非依存です。マルチプレイの有無に関わらずゲームコードは同じ API（Audio.PlaySe / Vfx.Spawn / Presentation.Play など）を呼ぶだけで、送受信の判断は Manager 内部と INetBridge の実装が行います。このページは INetBridge の全メンバー、シングルプレイとマルチプレイでの実装の違い、Host 権威モデルと偽造メッセージ対策、実機確認の結果をまとめます。

プログラマーが直接 INetBridge を呼ぶ場面は基本的にありません。 Audio / Vfx / Presentation などの Manager が内部で使うため、通常は各種 API ページ（Audio API 等）どおりに呼べばネットワーク対応も含めて動きます。このページは、独自のネットメッセージを追加する場合や、NGO 統合の配線・デバッグをする場合に読んでください。

INetBridge の取得

Packages/com.ddrive.core/Foundation/Net/INetBridge.cs で定義されるインタフェースです。実体は DDriveRuntimeBootstrap.Instance.NetBridge（起動配線の詳細は 起動配線（DDriveRuntimeBootstrap））から取得します。await DDriveRuntimeBootstrap.Instance.WhenReady; の後であれば確実に非 null です。

シングルプレイ持ち込み先向け: DDRIVE_NGO（2026-09-20 追加）

NGO（com.unity.netcode.gameobjects）は 必須依存ではありません。DDrive.Runtime/DDrive.Samples/DDrive.Tests.Runtime の各 asmdef が versionDefines で com.unity.netcode.gameobjects パッケージの有無を DDRIVE_NGO というスクリプティング定義シンボルに変換します。NgoNetBridge/NetDebugOverlay/NgoTransportConfigurator や、DDriveRuntimeBootstrap・PrefabDataValidator の NGO 関連コードは #if DDRIVE_NGO で囲まれています。

  • NGO を導入した場合（このリポジトリの既定）: DDRIVE_NGO が自動的に定義され、今までどおり NetBridgeMode.Ngo が使えます。手動で定義する必要はありません。
  • NGO を導入しない場合: DDRIVE_NGO が定義されないため、上記の型・分岐はコンパイル対象から外れます。DDriveRuntimeBootstrap.ResolveNetBridge() は Host/Client が要求されても警告を出したうえで LocalLoopbackBridge にフォールバックし（例外で止めない）、PrefabDataValidator は NetworkObject の存在検査をスキップします。シングルプレイ専用の持ち込み先で NGO パッケージを入れずに済みます。

これは Unity の「バージョン定義」の標準パターンで、Packages/manifest.json に com.unity.netcode.gameobjects が有るかどうかだけで自動的に切り替わります（プロジェクト設定を手で触る必要はありません）。詳細は Unity マニュアルの asmdef versionDefines と docs/42_distribution.md §2.3-9・§7 A-7 を参照してください。

ブリッジの選択

選択は DDriveRuntimeBootstrap.DefaultNetBridge（Inspector、NetBridgeMode.Loopback または NetBridgeMode.Ngo、既定 Loopback）と、起動時のコマンドライン引数（NetLaunchArgs.Parse、Runtime/Net/NetLaunchArgs.cs）で決まります。引数が Inspector の既定値を上書きします。

引数値意味

-ddrive-host文字列接続先ホスト（IP 等）
-ddrive-port整数ポート番号
-ddrive-sim-latency整数（ms）開発ビルドのみ有効。アプリ層の送受信キューに遅延を挟む（後述）
-ddrive-sim-loss0〜100（%）パケットロス率。パーサはこの値を受け取るが、実際にロスを起こす実装はまだ無い（後述の見送り事項）

NGO 利用時はシーンの構成が前提条件です。 Ngo モードを要求しても、シーンに NetworkManager と NgoNetBridge（DDriveRuntimeBootstrap.NetworkManagerRef/NgoBridgeRef の Inspector 直参照、未設定なら FindAnyObjectByType で自動検索）が見つからなければ、警告を出して LocalLoopbackBridge にフォールバックします（例外で止めない設計、CLAUDE.md §0-4）。また NetworkManager と NetworkObject（＝ NgoNetBridge）は同じ GameObject に置けません（NGO が [OnValidate] NetworkManager cannot be a NetworkObject と警告し機能しない）。NgoNetBridge は別の GameObject（例: NgoBridge）に置いてください。

開発用の手動接続（N-1 API + N-2 UI、2026-09-22 追加）

MS2026 のような複数人対戦（Host + 複数 Client）への持ち込みを想定した開発用テストプレイで、「実行中に接続先 IP を入力して接続する」ための仕組みです。-ddrive-net host/client は起動前に接続先を固定する必要がありますが、この Manual モードは起動後に接続先を選べます。開発ビルド/エディタ専用で、本編（リリース）の通常プレイには使いません。

起動: NetLaunchRole.Manual

-ddrive-net manual（または DDriveRuntimeBootstrap.DefaultNetBridge=Ngo かつ DefaultNetStart=Manual）を指定すると、ResolveNetBridge() は NetworkManager/NgoNetBridge の解決までは行いますが、Transport 設定と StartHost/StartClient の実行はどちらも呼び出しません。Start() の自動接続（StartNetworkingIfPending）は無害な no-op で終わります。

DDriveRuntimeBootstrap の手動接続 API

ランタイム UI: NetManualConnectOverlay

Runtime/Ngo/NetManualConnectOverlay.cs（#if DDRIVE_NGO）は、Unity Editor が無い実機（ビルド済み exe）でも IP を入力できるよう、上記 API を呼ぶだけの薄いランタイム UI です。NetDebugOverlay と同じ OnGUI 方式（専用の uGUI Canvas は使わない）で、NgoBridgeFactory.Create() が NetLaunchRole.Manual のときだけ、Debug.isDebugBuild || Application.isEditor を満たす場合に生成します（リリースビルドでは生成せず警告のみ）。

  • 画面左下に表示します（左上の NetDebugOverlay と重ならないようにするため）
  • IP / Port の入力欄、「Host で開始」「Client で接続」「切断」ボタン、状態 1 行（未接続 / Host listening / Client 接続中 / 切断）を表示します。状態は IsNetworkStarted・Bridge.IsServer/IsClient・NgoNetBridge.IsConnected から導きます
  • 接続中（IsNetworkStarted=true）は入力欄を編集できません
  • 入力検証は Runtime/Net/NetManualConnectInput.cs（Unity API 非依存の静的クラス）の TryParsePort/TryParse が行います。IP はIPv4 のドット表記のみ受け付け（ホスト名不可）、"localhost" だけ例外的に "127.0.0.1" に読み替えます。Port は 1〜65535 の数値のみ
  • 最後に接続した IP/Port は PlayerPrefs（DDrive.Net.Manual.LastAddress/DDrive.Net.Manual.LastPort）に保存し、次回起動時の初期値にします

詳細な設計・実機確認手順は docs/14_networking.md §14・§15、docs/29_network_device_test.md §23 を参照してください。

Host 引き継ぎ時の呼び出し順

複数人対戦で Host が切断した際、別の端末が Host を引き継いで試合を続ける構成向けに、D-Drive は「同一プロセスで StopNetworking() → 別ロールで StartHost/StartClient をやり直す」手順を前提として設計されています。呼び出し順序と、その際に内部で何が起こるかをまとめます。

呼び出し順

  1. Host 切断を検知した各端末が、まず自分で NetworkManager.Shutdown() を呼んでから DDriveRuntimeBootstrap.StopNetworking() を呼ぶ(NGO の Shutdown は非同期のため、既に停止済みの状態で StopNetworking() を呼んでも問題なく動く)
  2. 次に Host になる端末は、少し待ってから(待ち時間の長さは呼び出し側のゲームロジックが決める)bootstrap.StartHost(port) を呼ぶ
  3. 他の端末は、同様に少し待ってから bootstrap.StartClient(newHostAddress, port) を呼ぶ(再接続の認証情報等は呼び出し側が NetworkManager.NetworkConfig.ConnectionData に入れてから呼ぶ。D-Drive はその中身に関与しない)
StopNetworking() の直後、同じフレームで StartHost/StartClient を呼ぶことはできません。 NGO の Shutdown は非同期のため、NetworkManager.ShutdownInProgress が true の間は StartHost/StartClient は警告を出して false を返します。Shutdown の完了を待ってから(または一定時間待ってから)呼び出してください。

StopNetworking() で初期化される状態 / 保持される状態

StopNetworking()(および Client 視点で自分が切断されたとき)は、ネットワークに紐づく状態を自動的に初期化します。呼び出し側が個別にクリアする必要はありません。

Host 権威モデルと偽造メッセージの検証

D-Drive の「Server」は MS2026 の「Host」と同じ意味です。権威は Host にあり、Broadcast/SendTo は Host から呼ぶのが正規経路です。Client が Cosmetic 演出（SE/VFX 等）を出したいときは Server 宛 RPC で Host に「依頼」し、Host がレート制限と型登録を検証したうえで全員へ配ります（前節）。

発行者検証（HandleNetKey）: PresentationManager は演出ごとに発行する HandleNetKey（32bit）の上位 8bit に発行者（LocalClientId の下位 8bit）を埋め込み、IsAuthorizedSender(senderId, handleNetKey)（発行者一致、または Host からの信頼された中継/再送）で Signal/Cancel/Play を検証してから処理します。不一致は警告して破棄されます。この検証が機能するには「中継されたメッセージの送信元が誰か」を正しく伝える必要があり、以前は NgoNetBridge.Dispatch が受信メッセージの送信元を常に NetworkManager.ServerClientId（＝ Host）としてしまうバグがあり、発行者検証が原理的に機能していませんでした。RequestBroadcastRpc が rpcParams.Receive.SenderClientId（トランスポートが付与する真の値、Client は偽装できない）をそのまま中継するよう修正されています。

未知のキー宛の Signal/Cancel（対象の演出が既に完了している、または最初から存在しない）は、開発ビルドではキーごとに 1 回だけ「未知のキー、または対象の演出が既に完了しているため破棄しました」という警告ログを出します。

Host 以外による判定結果の偽装対策（2026-09-18 修正）: カタログ ContentHash の判定結果（CatalogContentHashResultMsg）は本来 Host だけが送るメッセージですが、NgoNetBridge.Broadcast は Client 発でも型登録済みのメッセージなら中継してしまうため、改造 Client が Matched=true を偽って送ると、Host が下した本物の不一致判定を上書きできてしまう欠陥がありました。CatalogContentHashGate に HostClientId（NGO の ServerClientId）を追加し、OnReceiveResultMsg の先頭で送信元が Host と一致するかを検証する（PresentationManager.IsAuthorizedSender と同じ発行者検証の考え方）ことで修正済みです。回帰テストは Tests/Runtime/CatalogContentHashGateTests.cs の ClientSide_ForgedResultFromNonHostSender_IsIgnored。詳細は docs/14_networking.md §7 実装メモ（2026-09-18）を参照してください。同じ形の穴が NetPongMsg（RTT 計測）にもあり、NgoNetBridge.OnPongMsgReceived の送信元検証で同様に修正済みです（2026-09-19、同ページ参照）。

D-Drive の版照合（ProtocolVersion、2026-09-20 追加）

接続時のカタログ ContentHash 照合（CatalogContentHashGate）は、GameData の内容を比較する前にまず D-Drive 自体の版を照合します。CatalogContentHashMsg に PackageVersion（string、表示専用）と ProtocolVersion（int、Foundation/Net/DDriveProtocol.Current）が乗っており、Host は受信した ProtocolVersion が自分の DDriveProtocol.Current と一致するかをContentHash の比較より先に見ます。

  • 不一致（旧版 Client など、このフィールドが無い版は既定値 0 として届く）は、ContentHash 不一致と同じ方針（CatalogContentHashPolicy.Decide: 開発ビルド/エディタは警告のみで継続、リリースビルドは切断）で扱われ、理由に「D-Drive の版が違います（自: x(Protocol n) / 相手: y(Protocol m)）」の形で双方の版が出ます
  • 一致すれば従来どおり CombinedHash（GameData の内容）の比較に進みます
  • PackageVersion 自体は照合しません（MINOR/PATCH の版差は互換のため、揃える必要があるのはワイヤ形式を表す ProtocolVersion だけです）
  • NetDebugOverlay（#if DDRIVE_NGO）に自分の版（CatalogContentHashGate.LocalPackageVersion）と、分かる範囲での相手の版（LastKnownRemotePackageVersion。Host は受信した Msg から更新できますが、Client 側は現状 Host の版を受け取る経路が無く常に空です）が表示されます

詳細な設計・互換性ルールは docs/14_networking.md §7・docs/42_distribution.md §5.6 を参照してください。持ち込み先の更新手順は Tools > D-Drive > Update > 更新ウィンドウ（docs/09_editor_tools.md §14）から行います。

実機確認（PC 2 台）

この仕組みは実機 2 台（PC-A Host + PC-B Client）での確認が済んでいます。詳細な手順・ログの見方は docs/29_network_device_test.md、確認済みの内容は以下のとおりです（最終版 v3）。

  • 遅延 0ms / 200ms: 接続・剣攻撃デモの Play/Signal・VFX 描画・アプリ層 RTT 計測（rtt_app_ms）を確認。UnityTransport.SetDebugSimulatorParameters が Obsolete で no-op になっているため、遅延は NgoNetBridge のアプリ層送受信キュー（ConfigureAppLayerSimLatency、開発ビルド限定）で代替実装している
  • Late Join: 接続直後に Host が保持する「アクティブ演出台帳」をスナップショット送信し、Client 側で復元されることを確認
  • 偽造メッセージ破棄: Client 役が周期的に送る偽造 PresentationCancelMsg（自分が発行していない HandleNetKey）が、Host・他 Client の両方で確実に破棄されることを確認（送信件数と破棄件数が一致）
  • 切断: Host 停止時に Client が [Net/Client] ... Host から切断されました を検知し、進行中のネット経由演出（VFX 含む）を PresentationManager.CancelAllNetworked() で後片付けすることを確認

既知の制約

ネット系のテストの穴 5 件は解消済みです（docs/41_phase6_review_2026-09-17.md「テストの穴」節、2026-09-18 対応）。偽造 CatalogContentHashResultMsg（上記「Host 権威モデルと偽造メッセージの検証」参照）・Host のカタログ登録前に届いたハッシュの保留のフラッシュ・タイムアウト経由の切断時の ClientDisconnectedForMismatch 発火・保留バッファ経由の偽造 Signal/Cancel・Cancel のレート制限（非 Host の Client 発）の 5 件すべてに回帰テストを追加済みです。実バグが見つかったのは CatalogContentHashResultMsg（送信元検証漏れ）の 1 件のみで、残り 4 件は追加したテストも green（実装は元々正しかった）でした。
